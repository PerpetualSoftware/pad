# Pad REST API reference

Moved verbatim from CLAUDE.md (TASK-3485), where it had pushed the file past Claude Code's 150k-character limit. New endpoint notes go here, not in CLAUDE.md.

## API

REST API at `/api/v1/`. Key endpoints:

- **`503 database_busy`: the database bound cut the request short** (TASK-4278; Postgres only). On Postgres every runtime connection carries a statement timeout, a lock timeout and an idle-in-transaction timeout. A request that runs past one of them (a stuck query, a lock wait that does not clear, a client holding a transaction open) used to hold one of the pooled connections until it finished or the connection died; it now fails with `503`, code `database_busy`, and `Retry-After: 2`. Two classes share the code and differ in what the message promises and in `Retry-After`. When the **server** cut the request short (a statement, lock or idle timeout, a deadlock, a serialization failure, a session terminated: the transaction rolled back), **a write that gets this answer saved nothing** and is safe to send again (`The server is busy; nothing was saved. Please try again.`). When the **client side** gave up or lost the connection (the request deadline, a dead or closed pooled connection, a network failure), the server may already have committed, so a write's message is `The server was busy and may not have finished this request. Check before trying again.` and does not claim nothing was saved; this class carries **no `Retry-After`**, because the text says to check first and the header would invite an automatic retry (the web client retries only GETs and the CLI only keyed writes, so neither changes; a missing header is a missing wait hint) (account deletion that hits its deadline before COMMIT is sent is the first class: the store proves nothing was committed; one that hits it during COMMIT is the second). A read says `The server is busy. Please try again.` for both. Clients key on the code, not the wording. A request whose client has already gone gets a header-only 503. A few sites carry their own wording where the main write had already committed (a credential change, a password reset, an item created whose parent link then timed out), and say what did commit; a cross-workspace copy keeps its "may or may not have landed, check the destination first" text, with no `Retry-After`. No body ever carries SQL, a SQLSTATE or a table name; the real error is in the server log. The settings (Postgres only, ignored on SQLite) are `PAD_DB_STATEMENT_TIMEOUT` (default `30s`), `PAD_DB_LOCK_TIMEOUT` (`10s`) and `PAD_DB_IDLE_IN_TX_TIMEOUT` (`60s`); `0` or `off` removes a bound, a malformed value refuses to start (see [deployment](deployment.md)). Migrations, startup backfills, `pad db migrate-to-pg`, `pad db release-cloud` and the other CLI database commands run unbounded. The long writers raise their own bounds for their one transaction: workspace purge and bundle import (30m statement, 5m lock), the attachment-reference remap (chunked, 30m/1m per chunk) and the `BackfillEffort` read. **Account deletion** (`POST /auth/delete-account`) waits out an in-flight workspace purge (measured 43 s) with a statement and lock timeout of `min(45s, time left)` inside a 50 s budget counted from request arrival (the Go server's write timeout is above it, and Pad Cloud's nginx `proxy_read_timeout` is 60 s); past it the answer is `503 database_busy` with the account intact. **Changed:** the document rename route (`PATCH` of a document title) used to answer a lock timeout or deadlock as `503 lock_contention` with `Retry-After: 1`; it now answers `503 database_busy` with `Retry-After: 2`. `lock_contention` remains only for a rename's link-cascade contention (`ErrLinkCascadeContention`). A 5xx the client sees as a plain 500 is no longer ever a database bound. The web client retries an idempotent `GET` on this code like a `429` (bounded by `Retry-After` and three attempts) and never retries a write by itself; the CLI never retries an unkeyed write, and a keyed write (`op_key`) takes its single keyed retry. An MCP caller sees a 503 as a transient upstream failure (`upstream_error` on the HTTP transport).
- **A workspace that does not resolve for the caller answers `404 not_found` with `details: {"scope": "workspace"}`** (BUG-3069) — a non-member and a deleted workspace alike, so it is not an existence oracle. A 404 about something INSIDE a workspace the caller can read (an item, a collection, a guest's ungranted item) carries no such marker. Code, status and message are unchanged from before the marker, so a consumer keyed on `not_found` is unaffected; key on `details.scope` to tell the two apart. A workspace addressed by UUID that the caller is not a member of answers `403 forbidden` instead, a separate refusal
- **A 403 from one of the shared gates names the gate in `details.reason`** (BUG-3864): `role` (the caller's workspace role is too low: `requireMinRole`, the edit check for a viewer, the grants list), `token_scope` (the API token's access does not include the action, i.e. a "Read only" token writing), `no_access` (not a member, a platform admin's bearer token on a workspace they are not in, an editor outside their collection access, a guest without the grant, or the cross-workspace check), and `workspace_not_authorized` (an OAuth connection's consent allow-list excludes the workspace; code `permission_denied`). Code and message are unchanged, so a consumer keyed on `forbidden` is unaffected. Any other 403 carries no reason, and its message is the only account of the cause. MCP reads the reason to tell the caller what to fix, on both transports; before this it said "Insufficient role" for every 403. An unverified Cloud email keeps its own code, `403 email_not_verified`, which MCP now reports as that code instead of `permission_denied`. A user-owned token minted with a `workspace_id` is refused outside that workspace with `token_workspace_pinned` (code `permission_denied`; `details.token_workspace` names the workspace while it exists, and is absent once it has been deleted; BUG-3982).
- `GET/POST /workspaces/{ws}/collections` — collection CRUD. `DELETE /collections/{slug}` ARCHIVES: a soft delete of the collection row, its items untouched and only hidden with it; nothing purges an archived collection (TASK-2189). A create or update whose `schema` has a field with no key, two fields with one key, or a select or multi_select field with an empty option or the same option twice answers **400 `validation_error`** naming it (`field key "status" is defined more than once`, `field "status" lists the option "open" more than once`, …), and nothing is written (TASK-3539): every client renders these as lists keyed by the value. It is a write check only: a schema already stored with a repeat still reads, an update that sends no `schema` still applies, and the web renders such a schema with each field and option once
- **Work or reference: `settings.tracks_work`** (PLAN-3535). `false` makes a collection REFERENCE material (docs, conventions, playbooks): its items do not count toward parent progress (every progress endpoint and the dashboard's active plans), do not block a parent from closing (`open_children`), stay out of a default report (`?collections` unset; naming the collection still includes it), and stay out of open-work counts (dashboard active items, attention, suggestions, `by_role`, `pad project next|ready|stale|standup|changelog`, the attention decision set, the admin `items_open`). They still count in the sidebar and dashboard summary totals, item lists, search and links. A workspace bundle written before the key existed imports its system collections as reference, as the migration marked them. **Absent means work**, today's behaviour, so old rows and writers that never send it are unchanged. A collection CREATE that does not set it gets `false` for a system collection and otherwise `true` iff its items can finish: its done field is a select and one of its options is terminal (its `terminal_options`, or the default terminal list when it declares none, so `open, done` counts). A NEW template Docs collection is created as reference, existing collections keep work except Conventions and Playbooks (migration 135 / PG 107), and owners flip any of them. Because settings are written WHOLESALE, an update whose `settings` omit the key KEEPS the stored value, never resetting it to work. A typed top-level `tracks_work` boolean on POST and PATCH sets that one key without touching the rest of settings, and is what the CLI (`pad collection create|update --tracks-work=true|false`) and MCP (`pad_collection` `tracks_work`, v0.81) send. Any non-boolean value is refused 400. An older server ignores the member and answers 200, so the CLI checks the response
- **Asks of a person: `settings.awaits_human`** (IDEA-3906 / TASK-3919). `true` marks a collection whose items are asks of a person (a human-tasks or asks collection); the needs-you router (a later unit) treats an open, assigned item in it as "asked". **Absent means false**, and no migration marks existing collections: owners set it per collection. Stored, carried and validated exactly like `tracks_work`: an update whose `settings` omit the key KEEPS the stored value, so turning it off takes an explicit `false`; a typed top-level `awaits_human` boolean on POST and PATCH sets that one key without touching the rest of settings, and is what the CLI (`pad collection create|update --awaits-human`, `--awaits-human=false`) sends; any non-boolean value is refused 400. An older server ignores the member and answers 200, so the CLI checks the response and fails rather than report a setting that did not land. Not on MCP yet. The web collection editor's Display tab carries the toggle ("Items are asks of a person").
- `GET /workspaces/{ws}/collections/{coll}/field-usage` — per field key, how many live items hold a value, and per string value how many hold it (TASK-2188): what the web schema editor shows before a field or option is removed. Owner-only plus full visibility, the PATCH's gates. The PATCH itself answers with an additive `omitempty` `warnings.orphaned` [{field, option?, items}] for each removed field, or option removed from a field that stays a select/multi_select, that live items still hold, read after the commit (a renamed option's migrated values are not listed). The values stay stored: a removed field's come back if a field with that key is declared again; a removed option's stay on their items, survive a `fields_patch` of other keys, and are refused on a write that sets them or a full `fields` blob that carries them. The CLI prints the list to stderr
- `GET /workspaces/{ws}/archived-collections`, `POST /workspaces/{ws}/archived-collections/{ref}/restore` — list archived collections (id, name, slug, prefix, icon, live `item_count`, `archived_at`) and restore one by id or slug, its items with it (TASK-2189). Owner-only, like the archive. A restore cannot collide: slugs are allocated unique across archived rows too, so a newer same-named collection took `x-2`. 404 for a ref that is not an archived collection of this workspace. The restore publishes `collection_updated`, and the item-sync epoch fingerprints the live collection set, so delta clients resync and receive the restored items. CLI: `pad collection archived` / `pad collection restore <slug>`; MCP `pad_collection` `list-archived` / `restore` (v0.72)
- `GET/POST /workspaces/{ws}/collections/{coll}/items` — item CRUD
  - **The list is bounded and paged** (BUG-3704; the same on `GET /workspaces/{ws}/items`). `limit` defaults to, and is capped at, **1000**; a missing, zero, negative or non-numeric `limit` means 1000. It used to mean every matching item with its body. `offset` skips rows, and it now works on the `?search=` path too (it used to be ignored there). Every response sets `X-Pad-Has-More: true|false`, and `X-Pad-Next-Offset: <n>` when there is more. The body stays a bare array. The order always ends on the item id, so offset pages neither repeat nor skip rows that tie on the sort. **Contract change:** a client that does not read these headers now gets the first 1000 rows of a longer list, not all of them. On this repo's own binary the CLI, MCP and web read them; an external or older client listing past 1000 rows must page. `pad item list` keeps its own 200 default for table and markdown output (and for any explicit `--limit`, including 0, which means the default), prints the exact next step on stderr when there is more, and takes `--offset`. With `--format json` and no `--limit`, it follows `X-Pad-Next-Offset` to the end (from `--offset` if given) and prints the whole array with no notice, since a consumer parsing the array never sees stderr (BUG-4024); it fails, rather than print a partial array, if the server's next offset does not advance or the list runs past 1000 pages. `pad_item` `list` (MCP) says `has_more` and never pages.
  - **At most 50 field filters** per list request (BUG-3703); more is a `400 validation_error` "invalid list filter: N field filters, at most 50", before any store work. Undeclared keys are checked in sorted order, and the check stops at the first one no item stores, which decides the 400.
  - **`?search=` keeps the list's filters** (BUG-3686): `include_archived=true` includes archived (soft-deleted) matches, and an explicit `sort` orders the matches. Without `sort` they come in relevance order, ending on the item id. These used to be ignored whenever the list carried a search term. **`tag` matches an element exactly** (BUG-3706): case-sensitive, with no wildcards, on both SQLite and Postgres. On SQLite it used to be a substring match that ignored case and treated `%` and `_` as wildcards. On Postgres, a tag holding a quote used to fail the request.
  - **`sort` on a select field ranks, it does not order by option text** (BUG-4400; the CLI's `--sort` and MCP `pad_item` `list` go through this same param). `priority` (and `severity`, the dashboard's fallback for it) use the dashboard's ranks, `models.PriorityRank` (critical > high > medium > low, case-insensitive) or `models.ConventionPriorityRank` on a field whose options are must/should/nice-to-have, so `priority:desc` is highest first and `:asc` lowest first on every collection, whatever order it declares its options in. A priority field whose options name no ranked word, and every other select field, sort in declared option order (`:asc` first option first, `:desc` reversed). Values outside the field's options sort after the known ones, and items with no value last, in both directions. The rank is per collection, so a workspace-wide list mixing collections puts every collection's highest priority first together. Non-select fields (dates, text, numbers) sort as before. Not covered: a non-priority select declared with different options in two collections interleaves by position, not by name.
  - **Field filters on the list:** any query parameter that is not a known list parameter filters on that field. **It must NAME a field** (BUG-3480): one the collection's schema declares (on the workspace-wide `GET /workspaces/{ws}/items`, one any collection the caller can see declares), else `400 validation_error` "invalid list filter ...". It used to answer `200 []`, which is how the web Library page's `?all=true` and WebMCP's `?collection=` went unnoticed. A key no schema declares but some item in scope STORES is still honoured (the BUG-2850 census of undeclared keys) and named in the `X-Pad-Undeclared-Filter-Keys` response header, which `pad item list` prints to stderr. A key that is not a field key (letters, digits, `_`, `-`) is refused too; the store used to drop it and answer the unfiltered list. `parent` / `plan` are consumed as the parent filter first, unless the collection declares a field by that name. A value containing a comma is an OR over its trimmed pieces (`?status=open,done`, which is what `pad item list --status open,done` sends). **Documented limit (BUG-3167):** over the query string, a literal value that itself contains a comma cannot be filtered for exactly, because the comma is the delimiter. A repeated-parameter form was declined, because an older server reads only the first value and silently narrows the result. The census when this was written found 0 comma-containing option values (2,025 select/multi_select options across 27 workspaces). In-process callers are unaffected: `store.ListItems` matches `ItemListParams.Fields` EXACTLY and takes an OR only through `FieldsAnyOf`, so the uniqueness check, playbook routing, and schema-driven completed-work and bootstrap queries match a comma value as itself
- `PUT /workspaces/{ws}/items/sort-order {updates:[{id, sort_order}]}` — set `sort_order` for many items in ONE all-or-nothing request (TASK-3517). The web's lane reorders (List, Board, ChildItems) use it instead of a PATCH per row, which spent a rate-limit token per row and, when a write in the middle was refused, left the server holding a half-applied order.
  - **Request:** `id` is a UUID or a ref; 1-1000 entries; a repeated item, however spelled, is a 400. The body is pairs rather than an ordered list because the client's plan leaves cards the caller can only view where they are.
  - **Permission** is the PATCH's, per item and before any write: visible, then editable (the app write rule, then the grant-aware edit check). It is NOT `/items/bulk`'s editor-role gate, so a guest holding an edit grant can reorder their item. An item the caller can't see answers the same 404 as an unknown id. One the caller can't edit refuses the WHOLE request with 403 `forbidden` naming it (`details.ref`). An item deleted between the checks and the write is 409 `conflict`. Nothing is written on any refusal.
  - **Effects per moved item** (an entry already holding its value is left alone): `seq` and `updated_at`, as the PATCH bumps them; an `item.updated` outbox event, with the batch folded under one `item.bulk_updated` header (`op: reorder`); one SSE `items_bulk_updated` per affected collection; and a `reordered` activity row with `sort_order_from`, `sort_order_to` and `reorder_batch` in its metadata.
  - **One row per item** keeps the activity feed's per-row visibility filter correct. The web feed, the dashboard's recent activity (`reorder_count`, additive) and `pad project activity`'s text and markdown output collapse a batch into one line AFTER that filter, so the count is what the reader can see. JSON activity stays per row.
  - **Answers** `{items:[{id, seq}]}`. Advertised as `item_sort_order_bulk` in `GET /server/capabilities`. The web does not probe it (its bundle is served by the same binary). Not on MCP.
- `GET/PATCH/DELETE /workspaces/{ws}/items/{slug}` — item by slug
  - **Identifier precedence (BUG-4119):** UUID, then current `PREFIX-NUMBER` ref, then exact, case-sensitive slug. A ref-shaped identifier containing any uppercase letter never falls through to slug; live resolution may accept an old ref proven by move history. An identifier with no uppercase letter tries only the current ref before its exact slug, never move history or a number-only fallback. Thus `task-5` still resolves current `TASK-5`, while `release-2` can name its own slug when no current `RELEASE-2` exists.
  - **Write responses (create/update) may carry `warnings.undeclared_fields`** (BUG-2850) — field keys stored in the item's `fields` blob that the collection's schema does not declare. They are ACCEPTED, not refused: a census found 168 live values under 14 such keys, and refusing them would break read-modify-write on items nobody edited wrongly. The element is additive and `omitempty`, so a clean write is byte-identical to before; system-written metadata (`implementation_notes`, `decision_log`, `github_pr`, `convention`) is excluded. The CLI prints the same list to **stderr**, never stdout, so `--format json` stays parseable
  - **Write responses may also carry `warnings.content_outcome`** (BUG-2995) — on a 200 it takes exactly one value, `applied_pending_flush`: the content went to the live collaborative document (a browser tab has the item open) rather than to `items.content`. It describes the WRITE, not the row's state at response time — a concurrent flush may already have updated the row, and the server does not re-read to find out. The response's `content` is then the markdown as **sent**, not as stored, and a read before a later `?source=collab-snapshot` flush lands answers with the PREVIOUS content — the lag, not a failed write. The stored form may also differ from the sent form: the markdown round-trips through the editor, so bullet markers, emphasis characters, list numbering and blank-line runs normalise, while already-canonical markdown survives unchanged (measured — `web/src/lib/collab/bug2995Roundtrip.svelte.test.ts`). No duration is claimed anywhere, and the flush is NOT guaranteed to happen at all (BUG-3000); since TASK-2198 U4 the server recovers the body itself after the tab's room closes, which bounds the window when recovery is on and the job succeeds, and nothing more. The CLI prints this to **stderr**, like the other write warnings, and since TASK-3132 the LAST line of `pad item update`'s stdout also names it (`— body sent to the open editor … a following "pad item show" will return the OLD body`), so it survives `| tail -1` and a discarded stderr; that last line reads `body replaced, A → B bytes` / `body cleared` on every other content write
  - **READ responses may carry `content_state`** (BUG-3000 / BUG-3033) — the read-side counterpart to `warnings.content_outcome` above, and its pending value is the same, `applied_pending_flush`. It has a second value no write produces, `superseded_set_aside` (BUG-3244): edits a collab schema-version rebuild set aside, which no tab can restore; see the set-aside bullet below. It wins when both apply, and a door that only marks staleness treats the two alike (`models.IsContentStateStale`, web `isBodyStale`) while any copy that names a remedy branches on it. A write warning says what a REQUEST did; this says what the ROW is: the item's op-log holds CONTENT-BEARING updates above `items.content_flushed_op_log_id`, so the body being served is BEHIND the live collaborative document. Since BUG-3124 rows that provably cannot change the document — y-protocols SyncStep1 frames, empty updates, and byte-identical re-sends of an earlier row (a SyncStep2 and an update differing only in their subtype byte count as identical since BUG-3136, which is what an open tab's answer to a joining tab is) — are persisted but marked `content_bearing = false` and not counted. Since BUG-3523 so is every SyncStep2 appended after it: a step2 is an answer to a peer's step1 and repeats content other rows carry, because a tab repairs its own possibly-missing edits with a full catch-up (an edit made offline, a socket that died, or a `barrier_ack` reporting a failed append). Rows classified before it, and the startup backfill, keep the older rule; they used to keep an item "pending" forever after its tab closed (measured: 470 pending items → 189 on the live DB). The classifier is envelope-only (no Yjs parse) and strict: a frame that does not parse exactly stays content-bearing. Additive and `omitempty`, and emitted only where a real body is — a summary or metadata projection that serves no content never claims its absent body is stale. The window is **bounded by server-side recovery** (TASK-2198 U4), not by a tab: when the item's collab room closes (60s after its last tab leaves) with content-bearing rows above the watermark, or when a one-minute sweep finds such an item dormant for 2 minutes with no room, a background worker materializes the WHOLE content-bearing op-log in a capped child process (`pad __materialize-worker`, internal/materialize) and `store.MaterializeFlush` lands it: cursor == MAX(op-log id), rows pending and no set-aside rows, checked in the write's own transaction under the collab item lock with no room open; watermark to the cursor only, `seq` bumped, one version row attributed `system` / `recovery` ("recovered from an unsaved editor session"), op-log NOT pruned. It never runs on a request path, and it is NOT a guarantee: a job that fails 3 times in a row is not retried until the op-log changes, an item with set-aside rows or rows from another schema version is skipped, and with `PAD_MATERIALIZE=off` the window is unbounded as before (the op-log GC's flush-coverage guard still RETAINS unflushed rows), so the row catches up only when a browser tab next opens the item. Opening it is now enough even when nothing needs flushing (BUG-3124 unit B): a caught-up tab whose document still renders to the stored body (byte for byte, or, since BUG-3197, as the editor's own serialization of it) calls `POST /workspaces/{ws}/items/{slug}/collab-watermark {op_log_cursor, content_sha256}`, and the server advances the flush watermark iff `cursor == MAX(op-log id)` and the sha256 matches `items.content`, atomically, writing no content, version, `seq` or `updated_at` — before this, a view that changed nothing was deduped and left the item "pending" forever. Web-client only; no CLI/MCP surface. The content is not lost — the op-log is the durability layer — but the marker is a signal to RE-READ LATER, never to re-send. The predicate is broader than "an API write is pending flush" and deliberately so: a user typing in an open tab produces the same stale body, and the row does not record WHY the op-log is ahead. Carried by every door that serialises `models.Item`, and by the hand-built ones too — the playbook `run` response, bootstrap convention and bodies-mode include payloads, the exported artifact's `provenance` block, and a line above the body in the MCP item resource. The CLI prints it to **stderr** (`pad item show --format markdown`, `pad playbook show`, `pad playbook run`), like the write warnings — except `pad item show`'s default TABLE output, which since TASK-3132 opens with it on **stdout**; markdown stays stderr because its stdout is the body verbatim for `update --stdin`
  - **`github_pr` is written only through typed update members** (BUG-2696): `github_pr: {number, url, title?, state?, branch?, repo?, updated_at?}` (number > 0 and an absolute http(s) url required, else 400) and `clear_github_pr: true`, mutually exclusive with each other and with a full `fields` write. A `fields_patch` entry naming it is refused like the other three reserved keys. The point is VALIDITY, not sender identity: any caller may send the member, but only a well-formed PR object gets in. `pad github link` / `unlink` / `project reconcile` use it and verify from the response that it landed; a server older than the CLI ignores the member and answers 200, which the CLI reports as an error naming the likely skew. Not on the MCP catalog
  - **Reserved metadata keys are refused in create's `fields`, and a full `fields` update may only CARRY them** (BUG-3163): `implementation_notes`, `decision_log`, `github_pr` and `convention` in an item CREATE's `fields` answer 400 `validation_error` and nothing is created. Convention metadata goes in through a typed create member, `convention: {category?, trigger?, surfaces?, enforcement?, commands?}` (an empty object is refused), which library activation uses on every surface (CLI, remote MCP, web library and Conventions pages); the CLI verifies from the stored fields that it landed, because an older server ignores the member. A FULL `fields` blob on update may carry a stored reserved value unchanged (compared as decoded JSON, not bytes), but a differing value or an OMITTED stored key (which would delete it) is refused with 400, checked against the row under the write lock. Use `fields_patch` for ordinary writes; it leaves unnamed keys untouched
  - **A convention's reserved `convention` copy follows its ordinary metadata keys** (TASK-2257). A convention stores its metadata twice: the ordinary fields `trigger`, `scope` / `surfaces`, `enforcement` / `priority`, `category` and `commands` (what agents obey; bootstrap and `--field` filters read them) and the reserved `convention` key (what `item.convention` prefers). When an update CHANGES one of those ordinary keys on an item that HAS a reserved copy, the server rebuilds the copy from the merged fields in the same transaction, after the carry check above: `surfaces` from `surfaces`, else `[scope]`; `enforcement` from `enforcement`, else `priority`; untouched keys keep their stored value. An item without a reserved copy is left as it was. The one new refusal is deliberate: a write whose merged values would leave the copy empty answers 400 `validation_error` and writes nothing. Before this, `pad item update --field trigger=X` left `item.convention` on the old trigger
  - **`refuse_undeclared_fields: true` is a strict opt-in on item update** (BUG-3156): a write that would store a field key the collection does not declare is REFUSED with 400 `validation_error`, and nothing is written, instead of being accepted and named in `warnings.undeclared_fields`. It refuses EXACTLY the keys that warning would have named: on a `fields_patch` write the patched keys only; on a full `fields` write the whole blob, stray stored keys included. It is additive and omitted by default, so a write without it is unchanged. **Skew:** a server that predates it ignores the member, which is the accept-and-warn, so a strict caller confirms by the ABSENCE of the warning rather than trusting a 200. `pad item bulk-update` and the remote bulk-update dispatcher set it; `pad item update` / `pad_item.update` do not
  - **A content write carrying a version token is REFUSED while a tab holds unflushed edits** (BUG-3133): 409 `content_pending_flush`, lifted by `overwrite_pending_edits: true`. The token guards the row, and those edits live only in the op-log until a tab flushes, so re-reading does not clear it. A tokenless content write still replaces them (edits the server has STORED; typing it has not received yet is the next bullet, and refuses tokenless writes too); with no tab open that deletes them from the op-log, and the response names how many in `warnings.pruned_pending_edits` (additive, omitempty; the CLI prints it to stderr). Rows a schema rebuild SET ASIDE (BUG-3244) refuse EVERY content write, token or not, with the same code plus `details.set_aside_rows`, because no tab will ever store them; `overwrite_pending_edits` deletes them in the write's own transaction and counts them into `warnings.pruned_pending_edits`. A collab-snapshot flush is exempt and leaves them alone. A writer that cannot carry a token asks for the same refusal with `refuse_pending_edits: true` (BUG-3230 U0): no row version is compared, and `overwrite_pending_edits` still lifts it. The web item pane's raw-markdown saves send it, because their debounced saves overlap and their unload flush is a teardown write (BUG-3080). Web-only: not on the CLI or the MCP catalog, so no tool-surface bump, and a server that predates it ignores it and replaces
  - **`POST /workspaces/{ws}/items/{ref}/patch {edits:[{old, new, line_hint?}], expected_seq?}`** (PLAN-3578 step 1) replaces exact text in the body without sending all of it.
    - **Rules:** each `old` must occur EXACTLY ONCE in the body as it stands inside the write's own transaction (overlapping occurrences count), and `line_hint` only chooses among several exact matches. Edits apply in order, all or nothing, at most 100 per patch.
    - **Answer:** `{ref, seq, patch_id, version_id, rebased, intervening?, diff}`, where `diff` is a unified diff of the body before → after. Every patch writes a version (past the throttle), and its activity entry carries `patch_id` and `patch_edits`.
    - **`expected_seq` does NOT refuse;** the anchors are the precondition. When the row's seq moved, the patch still applies if every anchor matches and answers `rebased: true` with `intervening: {from_seq, to_seq, changes:[{activity_id, seq, prev_seq, action, actor, source, at, version_id?}], complete, truncated?}` (at most 50 changes).
    - **`complete`** is decided by walking the activity seq chain. Every item `created`/`updated` activity entry carries `metadata.{prev_seq, seq, version_id?}`. A write that left no stamped entry (a path that writes none, a failed activity write, anything before the stamps existed) breaks the chain, and then `complete` is false. A debounced merge keeps the chain only across contiguous runs, and marks the entry `seq_chain_broken` otherwise. `internal/store/plan3578_seq_site_guard_test.go` classifies every seq-moving store statement.
    - **Refusals** (nothing written): 400 `bad_request` for no edits or an empty `old` (`details.edit`); 400 `bad_request` for an edit whose `old` equals its `new` (`details.edit`), or edits that together leave the body as it was (`details.ref`), on both the no-room and open-editor paths, since every patch is a version; 409 `patch_anchor_missing` (`details.edit`); 409 `patch_anchor_ambiguous` (`details.edit`, `details.lines`); 409 `patch_room_open` when only an editor that cannot apply patches holds the item (no patch-capable tab, never a whole-document replace). Also every PATCH guard: unflushed editor edits refuse it as `content_pending_flush` token or not, set-aside rows, permissions.
    - **Open item (step 2):** when a live editor holds the item, the patch goes to a patch-capable tab (one that connected with `?patch_capable=1`; only such a tab is ever sent one, because an older tab would read an edits-only request as an empty body). The tab applies it to its LIVE document as a narrowed replace of exactly the changed top-level blocks, aligning blocks under a defined equivalence (equal, or differing only in a link's title or bold/italic on whitespace; a trailing empty paragraph is ignored). It acks with the canonical `before`/`after`, from which the server builds the diff. A row write then records the patched body as a version attributed to the request (`ExternalContent`) and moves the seq; the answer adds `content_state: "applied_pending_flush"`. Unflushed editor edits do not refuse it, because the tab applies to the document that holds them. The tab refuses `patch_unstable_roundtrip` (`details.line`, `details.reason`) when a changed block has no equivalent live block. Refusals are counted in `pad_patch_refusals_total{reason}`.
    - **Undo (step 3):** `{undo: "<patch_id>"}` instead of `edits` inverts a stored patch. Every patch records its applied edits in `item_patches` (`{old, new, ctx_before, ctx_after}`, the context up to 40 characters each side of the replacement as it stood right after that edit, clipped at line ends, except as below) in the same transaction as its version row, on both paths. The undo anchors each inverted edit on `ctx_before + new + ctx_after`, in reverse order, under the ordinary rules, so it refuses (`patch_anchor_missing` / `patch_anchor_ambiguous`, nothing written) when that text has changed since: it never reverts someone else's later edit. The undo is itself a patch (its own `patch_id`, version and record) and answers with `undo_of`. An edit that emptied its line records context reaching across the line breaks, so its undo still has an anchor; when the patch emptied the WHOLE body there is nothing to anchor on, and the undo is refused 400 `bad_request` pointing at History, which holds the patch's version. 404 `patch_not_found` when the id is not a patch on this item (workspace-scoped, and checked against the item inside the transaction); 400 for `undo` together with `edits`. `item_patches` has no read surface besides undo and is not exported; it goes with its item (`ON DELETE CASCADE`, plus the workspace purge list).
    - **Idempotency keys (TASK-3585):** an `Idempotency-Key` header, or `op_key` in the body (not part of the request), makes a retry safe. The key is claimed per (workspace, user, key) BEFORE any write-path guard (so a retry of a write that committed replays it instead of meeting its own success as a conflict), with a 60s lease, and its answer is recorded INSIDE the write's own transaction, guarded by the claim token: `done` holds exactly when the write committed, so a claim whose lease expired committed nothing and may be taken over. A retry of the same request (route + item + canonical body) answers the stored result with `Idempotent-Replayed: true`; another request under the key is 422 `idempotency_key_reused`; a live claim is 409 `idempotency_in_flight` (`Retry-After`). Refusals are not stored: the key is released, so a corrected retry with the same key proceeds. When an open editor received the patch and never confirmed it, the key records the patch id and that connection; a retry goes ONLY to that connection, whose tab remembers the patches it applied and re-acks one it is sent again. With that connection gone it answers 409 `patch_outcome_unknown` (`seq`, `base_seq`, `diff` since then) and re-applies nothing, because an insert-shaped edit would keep its anchor elsewhere. Keys live 24h (swept); capability `idempotency_keys`. The CLI sends a fresh key per invocation and retries once with it on a transport error or a 5xx, and only when the server advertises `idempotency_keys` (an older server ignores the key, so a retry there could write twice).   - **Schedules on copy and move** (TASK-4104 D3). The source item's schedule (see **Item schedules**) travels through the same door a bundle import uses, and is armed FRESH in the destination: timing, kind, audience, lead, `anchor_wall`, commitment roles, outcome and roles origin carry; the resolved-occurrence history does not; a COPY never carries a snooze; the outstanding occurrence is the first one strictly AFTER the copy instant, so a copy never fires an occurrence that is already due or past. The one exception is a MOVE (`archive_source`) of a source whose outstanding occurrence is DUE (its instant is at or before now), whether it has FIRED and is unresolved or has NOT fired yet (the tick lags): the move ends the source, so the destination carries that occurrence once and fires it on the next tick rather than it vanishing, and a one-shot in that state is not reported `exhausted` (a recurring schedule then continues on its grid once it is resolved). Fire and move serialise on the item, so it fires once per door at most. A plain copy never does this: the source still holds it. A MOVE carries a snooze still ahead of now as the frozen instant (see the resolve section under **Item schedules**), both when carrying the due occurrence and when the destination's first occurrence is the source's own pending one (matching by wall for floating schedules, by instant for pinned schedules); a spent snooze is dropped. A MOVE also carries overrides for the same outstanding occurrence and the source schedule journal, remapping its IDs and causal references before appending a fresh `carry` marker. A COPY has fresh history: only its `carry` marker is written, with no occurrences or overrides. A MOVE also ENDS the source schedule in the same transaction (`ended_at` set, no outstanding occurrence, the managed reminder deleted, history kept), so restoring the archived source cannot fire a second copy of a schedule that now lives in the destination; an edit of its schedule made after the move answers 409 `archived`, and so does one racing the move (the store re-checks the item under the schedule lock, and the handler re-reads the item to give the same answer; 404 only if the item is truly gone), so neither can revive it. A same-workspace move changes nothing about the schedule. A FLOATING schedule is read in the DESTINATION's recipient zone: the destination item's assignee when one carried (a member of the destination), else the copier. A pinned schedule keeps its zone. The copier is the signed-in ACCOUNT that owns the new item, the same one later reads use. When a copy or move CHANGES a floating schedule's recipient (its assignee is not a member of the destination, so the copier's zone applies), the destination walks its walls in the new zone, so a wall the source already fired can fire again there (going west), or one can be skipped (going east); arming strictly after the source's last fired instant is TASK-4221. The `warnings` block of BOTH the preflight and the copy result carries ONE additive object, `schedule`, present whenever the SOURCE has a schedule and absent otherwise: `{carried, history_dropped, changes_dropped, skipped?}`. `carried` is true when the destination got one; `history_dropped` is how many resolved occurrences the source schedule has (a copy never carries them); `changes_dropped` is how many journal rows of the source schedule do not reach the destination: every row on a copy or when nothing is carried, and on a carried move the rows the restore refuses (an orphaned or invalid row), counted by the same function in the preflight and the copy; `skipped` is `{reason}`, present only when it was NOT carried. Inside the object `carried:false`, `history_dropped:0` and `changes_dropped:0` are always written, so a client can tell "skipped" from "no schedule" from "an older server" (no object). `reason` is `ended` (the source schedule has ended), `exhausted` (its rule has no occurrence after now), `timing:<code>` (the rule no longer compiles or cannot be walked: a schedule code or `cap_*`), or another carry reason from the import vocabulary (`<field>:<code>`, `invalid`). **A move never ends a live schedule it did not carry.** `ended` and `exhausted` are TERMINAL (nothing is left to fire): a copy skips and reports them, and a move ends the source (if it is not already) and reports them. Every other reason is NON-TERMINAL (the schedule is live and the destination cannot take it): a plain copy still skips and reports it, but a MOVE is REFUSED and rolled back whole (nothing is written in either workspace, the item stays where it was) with **409 `schedule_not_carried`**, `details: {reason}`; copy the item instead, or repair the schedule. The move-only NON-TERMINAL reasons also include `exhausted_in_destination_zone` (a floating MOVE whose rule has no occurrence after now in the destination recipient's zone while the source's own outstanding occurrence is still ahead in its zone) and `schedule:unreadable` (the source's outstanding occurrence cannot be read): both refuse the move with 409; a copy in the same state reports `exhausted` for the former and keeps its usual carry result for the latter. `timing:cap_time` is load-dependent, not a property of the schedule, so it refuses a copy AND a move with **503 `schedule_busy`** and `Retry-After: 1`, as every other schedule write does; retry. The preflight answers the same 409 or 503 for the request the copy would refuse, from one store function. A floating schedule's preview reads the destination recipient's zone (the carried assignee, else the copier), through the same function the copy uses. A copy and a cross-workspace move do NOT carry a milestone's forecast, selected children or completion evidence (see "Milestone forecasts and outcomes"); the `schedule` object also carries `forecast_dropped` (0 or 1) and `children_dropped` (the selected children the requester can read, never a count that includes one they cannot), identical on the preflight and the copy result. A same-workspace move keeps the forecast and the selection with the item. These are not `dropped_fields` entries.

**Authorization is decided when a request is admitted, not re-checked at the write** (BUG-3804, by policy). `RequireWorkspaceAccess` reads the caller's membership, role and guest grants once, before the handler runs. A handler's own permission and visibility checks (`requireEditPermission`, `requireItemVisible`, owner-only gates) likewise run before the store transaction that writes. As a rule, none of these is re-read inside that transaction. A few writes do re-check inside it: some app-install writes re-check the owner (`requireWorkspaceOwnerTx`), and credential mints re-check that the user is still active (`requireActiveUserTx`). Those are local hardening, not the contract. So a request already admitted when its caller is demoted, removed, restricted from a collection or loses a grant still completes, and the change applies from the next request. The window is one request's duration. Long-lived connections are the exception, because their "one request" has no end: they re-check the principal (membership, item visibility) and the credential on each revalidation tick (next paragraph). The policy covers the CALLER'S authority only. The data a write decides on (a referent's liveness, a unique holder, a guard's count, the body a patch is computed from) is not covered: a write that acts on a stale read of it is a bug, as BUG-3811 through BUG-3817 are.

**Every long-lived connection ends when the CREDENTIAL that opened it stops being valid** — both SSE endpoints, the `/api/v1/collab/{itemID}` WebSocket, and the MCP transport's long-lived streams (a GET stream and a `subscriptions/listen` POST, on `/mcp` and `/mcp/chatgpt`), checked on each connection's revalidation tick (BUG-3007; MCP since BUG-3837, every ~60s, the `/events/stream` cadence). The invariant is deliberately wider than "the session was destroyed": a revoked PAT ends a stream too, because a revoked PAT still streaming is the same defect for a CLI or MCP caller that a destroyed session is for a browser. Before BUG-3007, the two SSE endpoints and the collab WebSocket kept running indefinitely — measured at 150-180s past a logout, and 64-120s past a revocation, in both cases with `/auth/me` on that credential answering `401`. The pre-existing per-tick checks are about the PRINCIPAL (is this user still a member, is the item still visible) and none of them changes when a credential dies, which is why the two are separate questions rather than one. A request carrying NO credential AND no resolved principal — the fresh-install window, the legacy no-auth path — is unaffected: there is nothing to invalidate. A request that carries a resolved USER but no record of how the credential was established is CLOSED, not exempted: the middleware stamps that on every accept point, so its absence means an accept point recorded who without recording what, and a connection nobody can re-check is the same defect under a new name. (Both MCP accept points record their kind: a PAT is re-checked as `api_token`, and an OAuth access token is re-introspected, so a revoked token, a revoked grant (a Connected Apps revoke) or an expired token ends the stream. An OAuth stream therefore ends when its access token expires, and also when the client refreshes, since a refresh rotation revokes the old access token; the new token was never presented on that stream, so the client must reconnect (and re-issue a `subscriptions/listen`) to keep receiving notifications. Nothing on the stream says why it ended: a GET stream just closes, and a listen ends with its ordinary (empty) result, so a client that wants notifications re-listens whenever a listen returns. An MCP stream also ends when its user is deleted or disabled. No revocation kicks an MCP stream at once: each ends at its next tick, so within about one interval.) A store ERROR is not a revocation and keeps the connection until the next tick, so a database blip does not disconnect the fleet.

Both SSE endpoints share one admission budget, enforced **per instance**: `PAD_SSE_MAX_CONNECTIONS` (default 1000) and `PAD_SSE_MAX_PER_USER` (default 50) cover both, and the MCP transport's long-lived streams too (BUG-3835: a GET stream and a `subscriptions/listen` POST, on either MCP mount, `/mcp` or `/mcp/chatgpt`. Only a POST whose `Mcp-Protocol-Version` header is a modern version the transport serves is read to find a listen, since mcp-go serves a listen on no other; any other POST reaches the transport, so a client probing an unserved version gets its unsupported-version `400` and falls back. Pad serves only the legacy MCP protocol versions today, so no listen is counted and no POST body is read for admission. A tool call that the transport upgrades to SSE mid-call is not counted, since a refusal there would land after the call's side effects). `PAD_SSE_MAX_PER_WORKSPACE` (default 100) covers `/api/v1/events` only. Over the limit is `429` with code `sse_limit_exceeded` and a `Retry-After` header, on an MCP stream before the transport runs — clients must back off, not retry immediately (BUG-2726). The CLI does; browsers cannot, since `EventSource` exposes neither the status nor the header to the page (BUG-2733). On `/api/v1/events` only, callers with no resolved user (a legacy workspace token, or the fresh-install window before the first admin exists) are bounded per *workspace* instead of per user; `/api/v1/events/stream` has no such case — it requires a resolved user and answers `401` otherwise.

MCP event streams also carry a `: keepalive` comment at the `/events` cadence, as `/events` does. It keeps an idle stream alive through proxies, and it ends a stream whose peer is gone even when no notification is due: the next keepalive write fails once the connection is known dead, within a keepalive or two after a reset (the first write after a reset can still succeed), or once TCP gives up on a half-open peer. It does not catch a live client that holds the connection open and stops reading: a comment every keepalive interval takes days to fill default socket buffers, so no write blocks long enough to time out. On every stream, that client is bounded by the admission budget above, not detected.

Collab WebSocket dials (`/api/v1/collab/{itemID}`) are NOT in the general API bucket (BUG-1308): they draw on their own per-user bucket (5/s, burst 50), so a user's dials and REST calls never refuse each other, and `PAD_COLLAB_MAX_PER_USER` (default 50, **per instance**) bounds how many sockets one principal holds. One browser tab's content writes to an item are ordered by the server, also **per instance** (BUG-3080). Every item-pane content PATCH carries `client_write: {tab, n}` — a random id minted per page load (never a session or user id) and a counter that only rises — and a write whose `n` is below one already APPLIED for the same (item, tab) answers `409 superseded_write` (details name the `n` it lost to) and writes nothing; the pane treats that as success and never retries it. It exists for the teardown flushes, which are both dispatched before the tab sees either result, so no version token can order them (both would carry the same `expected_seq`, and the older landing first would get the NEWER refused — which is why those writes carry none). The mark is one in-memory map keyed (item, tab), bounded at 10,000 keys and forgotten after 10 minutes idle: it is lost on restart and not shared between instances, so on a multi-instance deployment it is best-effort. A missing mark refuses nothing, so every one of those gaps degrades to the behaviour before it existed, never to anything worse. A write with no `client_write` (the CLI, MCP, any other API caller) is never compared against a mark. Refusals are counted in `pad_content_writes_superseded_total`.

### Sessions and presence

`GET /api/v1/sessions` lists only the authenticated user's live event-stream
connections, oldest first: `{sessions: [...], count}`. There is no admin view or
user selector. Each row carries `id`, optional `label` and `pid`, `armed`,
`bearer_auth`, `connected_at`, optional `agent` and `worker`, and `state`.
`worker` is the same short display form as lease reads (`wk_3f2a`); the full
worker id is never returned by this endpoint. The response is private and not
cacheable, and an empty list is `sessions: []`.

The stream's `X-Pad-Agent` is trimmed, stripped of control characters and
limited to 64 runes, using the write-attribution rules. `X-Pad-Worker` must be
`wk_` plus 32 lowercase hex characters; an invalid value is silently dropped
when opening the stream. These are self-declared connection facts, like label
and pid, not verified identities. The CLI's worker id stays stable across
Claude Code `/clear` and stream reconnects; each connection still gets a new
session id.

`POST /api/v1/sessions/activity` accepts `{"state":"busy"}` or
`{"state":"idle"}`, with an optional client timestamp `at` in RFC3339 or
RFC3339Nano format (for example `{"state":"busy","at":"2026-10-23T12:00:00.123456789Z"}`),
and requires a valid `X-Pad-Worker`. Success is `204` with no body, including
when a reordered report is ignored. A report is ignored only when both it and
the stored record carry client timestamps, its timestamp is strictly older,
and the gap is at most 10 seconds, inclusive (the 3s report bound plus 7s slack).
This reorder window covers the
child's three-second bound plus spawn and scheduling slack for reports racing
in flight. An older timestamp beyond the window applies as a clock step;
an equal or newer timestamp also applies. A report without `at` always applies
and clears the stored client timestamp, so the
next timestamped report wins. An explicit null `at` is malformed; omit the field instead.
Missing or malformed worker: `400 invalid_worker_id`;
malformed body, timestamp, or any other state: `400 validation_error`.
It records activity under the credential's user plus worker, independently of
session ids. A different user claiming the exact same worker cannot change the
caller's presence.

A session is `busy` when its worker has an unexpired busy record. Activity
expires 30 minutes after server receipt, independently of client clock skew,
and an accepted idle report clears busy immediately. Client timestamps order
reports from the same worker; server receipt time controls the busy window and TTL.
Otherwise `state` is `online` when `armed` is true, or
`connected_not_accepting` when false. A session without a worker is never
busy. State does not change push consent or delivery rules.

The Claude Code hooks set busy on `UserPromptSubmit` and clear it on `Stop`.
Claude Code fires no `Stop` when the user interrupts a turn with Esc, so an
interrupted session reads `busy` until its record expires 30 minutes after
the prompt report reaches the server. Nothing refreshes the record mid-turn:
a single turn longer than 30 minutes reads `online` or `connected_not_accepting`
for the rest of the turn, according to its armed state.

Both endpoints require a resolved user (`401 unauthorized` otherwise) and
answer `503 unavailable` when the presence registry is absent or cannot be
read/written. The list endpoint reads activity in one batch. A failed batch
leaves all sessions `online` or `connected_not_accepting`; an undecodable entry
only affects that worker's sessions, and other workers retain their activity
state. Either failure logs one warning per request and the list still answers
`200`. Workspace-pinned PATs are refused by the existing pin policy.
A hook running with a read-only API token cannot report activity (`POST /api/v1/sessions/activity` is refused with `403`) and silently does nothing.
`pad session activity <busy|idle>` is intended for hooks: silent, no prompts or
server startup. It captures the client timestamp and returns immediately while
a detached background child sends the report, so a prompt never waits on the
network. The child has a three-second overall deadline and a two-second HTTP
request timeout within it. Argument errors, flag errors, configuration failures,
network failures and spawn failures are silent and exit 0. `--help` prints help
to stdout; the shipped hooks never pass it. An OS-level kill cannot be converted
to exit 0. If session identity cannot be resolved within 500ms, that report is
sent without a worker id and the server drops it with `400 invalid_worker_id`.
The next prompt or stop retries resolution and corrects activity once identity
resolves. It is not an MCP tool.

### Workspace-pinned tokens (BUG-3982)

A user-owned API token minted with a `workspace_id` is confined to that workspace. Before BUG-3982 the pin was recorded and ignored: the token reached every workspace its user belonged to. Unpinned tokens, cookie and CLI sessions, OAuth connections and legacy user-less workspace tokens are unchanged.

- **Workspace routes** (`/workspaces/{slug}/...`, by slug or id), the collab socket, `/events?workspace=`, the `/-/r/{workspace}/{ref}` resolver (its ordinary 404), cross-workspace item copy and move, and backlinks answer a pinned token for its own workspace only. A refusal is `403 permission_denied` with `details.reason: "token_workspace_pinned"` and `details.token_workspace` (the slug; absent when the pinned workspace has been deleted); the message names the workspace and says to mint an unscoped token (`pad token create --name <name>`, or Account settings, API Tokens). On the doors that take a workspace by name (`/workspaces/{slug}/...`, `/events?workspace=`, `/search?workspace=`, the copy and preflight `target_workspace`, and the `/-/r/{workspace}` resolver, whose answer is its 404) the refusal is decided before the name is resolved, so it is byte-identical for a workspace that does not exist, one the user is not in, and one the user is in.
- **Cross-workspace reads narrow.** `GET /workspaces` lists the pinned workspace only, and an unscoped `GET /search` searches only it. `GET /search?workspace=<other>` is the one search refusal (403, decided before the slug is looked up).
- **Global routes are refused**: anything not workspace-scoped other than the permitted doors below (workspace create, import, deleted and restore; `/auth/export`; `PATCH /auth/me`; invitations; workspace tabs; UI dismissals; `/events/stream` and `/watches`; sessions; connected apps; admin; the rest). The five `/me/workspace-groups` routes and all three calendar feed management routes (`POST /me/calendar-feeds`, `GET /me/calendar-feeds`, `DELETE /me/calendar-feeds/{id}`) are refused too. The allow list is `pinnedTokenRouteAllowed` in `internal/server/pinned_token.go`, deny by default, so a new global route is closed to a pinned token until it is listed.
- **Stays open**: `GET /auth/me`, `GET /auth/session`, `GET /auth/tokens` and `DELETE /auth/tokens/{id}` (revoking is the incident path), `GET /me/needs`, `GET /me/agenda`, the pre-auth flows, and the public routes. A public route that reads the caller (an email-restricted share link, the invitation preview) treats a token pinned to another workspace as signed out. The token doors are narrowed to the tokens pinned to the same workspace, the caller included: `GET /auth/tokens` lists only those, and `DELETE` of any other id (the user's unpinned tokens, tokens pinned elsewhere) is the same `404 not_found` as a missing id.
- **Remote MCP** (`/mcp` with a PAT) meets the same gates: tools, `pad_set_workspace` and `pad://` resources see the pinned workspace only.
- **A pin whose workspace was deleted** fails closed: every workspace door is refused (the message says the workspace no longer exists) and lists and searches are empty.
- **Known gap**: the unscoped search lists memberships, so a pin on a guest workspace (BUG-3914) finds nothing unscoped; `workspace=<pin>` works.

### Chat conversations (TASK-4039)

Chat is global, with no workspace or admin bypass: admission is by conversation membership only. Stage 2a direct conversations join an owner and one of that owner's own agents. Conversation `number` is a positive integer in the owner's namespace, not a global identifier. Malformed numbers and sequence path segments, missing conversations/messages, other users and non-member agents return the same `404 not_found` response, `Conversation not found`.

All routes below are under `/api/v1` and require a signed-in human account: no user is `401 unauthorized`, an app context or app-kind user is `403 forbidden`. Legacy userless tokens are refused `403 legacy_token_not_allowed`; workspace-pinned PATs are refused `403 permission_denied` with `details.reason: token_workspace_pinned`. Read-scoped PATs may GET but cannot POST or DELETE (including marking read). Disabled accounts are refused by authentication; unverified accounts cannot mutate under the standard verified-email gate. Cookie writes require CSRF.

The actor and send author are always `(authenticated user ID, agent key)`. Cookie sessions are always the human (empty agent key), ignoring `X-Pad-Agent`. Bearer callers use the existing trimmed, control-stripped `X-Pad-Agent` label, truncated to 64 runes regardless of byte length, as attribution and presence do (BUG-4055). An in-process remote-MCP caller without a declared agent name is refused `403 agent_name_required`. Source is derived from the credential (`cli` for bearer, `web` for cookie). Body fields such as `author_user_id`, `author_agent_key`, `source`, `seq` and `agent_key` cannot override a message's author or source.

A human's `agent_key` on `POST /me/conversations` must already be a normalised agent name (the form `X-Pad-Agent` produces): no leading or trailing whitespace, no control characters, and at most 64 runes; otherwise it returns `400 validation_error`, `agent_key must be a valid agent name`, without spending a ChatDM token. This body field is an explicit identifier, so it is refused rather than silently changed. Two declared names that share their first 64 runes map to the same agent key, deliberately the same as in attribution and presence.

**Provenance caveat (TASK-4039 / TASK-4041):** `X-Pad-Agent` is self-declared attribution, not authentication. A holder of the owner's credential can choose another agent label within that owner's namespace, or omit it and post as the human, also avoiding the agent send bucket (the general API limit still applies). An owner-authored message is therefore **not authenticated as human input**. Stage 2a accepts this because both conversation members represent the same owner and credential authority; it must not be presented as a verified human channel. Owner-authored messages are framed as information by default (TASK-4041); `pad chat arm --accept-instructions` opts this session into an unauthenticated channel controlled by the agent's own credential holder. The framing rules are under `GET /api/v1/events/stream` above. A verifiable human channel would require a credential the agent cannot hold.

Wire types are explicit projections; `owner_user_id`, `dm_key`, `author_user_id`, raw `context_workspace_id` and `op_key` never appear in responses. `Conv` is `{id, number, kind, title, agent_key, last_seq, created_at, updated_at}`. `kind` is `"direct"` or `"group"`; stage 2a creates only `"direct"`. `ConvDetail` adds `{read_seq, unread}`. The single-conversation GET additionally includes the caller's own `delivered_seq`; inbox rows omit it. `ConvSummary` adds optional `last_message: {seq, author_agent_key, author_is_human, excerpt, deleted, created_at}` to the detail; it never includes a full body. `Msg` is `{id, conversation_id, seq, author_agent_key, author_is_human, mine, source, body, reply_to_seq?, reply_to?, context_workspace?: {slug, name}, created_at, deleted, deleted_at?}`; `mine` compares both components of the author and actor pair. `reply_to` is `{seq, author_agent_key, author_is_human, excerpt, deleted}`, the store's bounded quote preview.

On unread, the actor never comes from the query: for an agent the supplied `agent` must equal its header key; for a human a nonempty `agent` filters their own rows. Only rows with `unread > 0` are returned. All response lists, including an empty `messages` page, are arrays, never `null`. Humans may delete their own or their agent's messages; an agent may delete only its own.

Store errors map through one handler helper:

| Sentinel | HTTP / code | Message |
| --- | --- | --- |
| `ErrConversationNotFound` | 404 `not_found` | `Conversation not found` |
| `ErrInvalidConversationInput` | 400 `validation_error` | Static store validation detail |
| `ErrConversationForbidden` | 403 `forbidden` | `You can only delete your own messages` |
| `ErrReplyTargetNotFound` | 422 `reply_target_not_found` | `Reply target not found` |
| `ErrReplyTargetDeleted` | 409 `reply_target_deleted` | `Reply target was deleted` |
| Anything else | 500 `internal_error` | Generic; store diagnostic is logged, never returned |

Pagination defaults to 50 messages, clamps to 200, and returns ascending sequence order, including tombstones (`body: ""`, `deleted: true`). Cursors are exclusive nonnegative integers; both cursors together, nonintegers and negative cursor/limit values are `400 validation_error`. A zero limit uses the default. Without `after_seq` the page looks backward from the newest messages (or before the cursor); with it the page looks forward. For a nonempty page, `has_more` means older messages iff `oldest_seq > 1`, or newer messages iff `newest_seq < last_seq`, in the requested direction. Empty pages have zero oldest/newest sequence and `has_more: false`.

Sending moves the **author's own** read marker to the message it just took (BUG-4320): that is the newest message at the moment of the send, so a reply covers everything before it, and a message that arrives after it stays unread. The move is in the send's transaction and forward only; it never touches `delivered_seq` or another member's marker, and an `op_key` replay moves nothing. `POST /read` takes the sequence the client **displayed**, moves monotonically and clamps to `last_seq`. `POST /delivered` uses the authenticated chat actor and advances only that member's `delivered_seq`, monotonically and capped at `last_seq`. It does not mark messages read. The monitor acknowledges a contiguous run of fetched sequences above its fetched per-conversation floor that are successfully printed (including already-printed rows), the agent's own (`Mine`), or tombstones (a retraction prints only when the original was printed); a missing sequence or event id mismatch stops both the fill and the ack. A duplicate message event outside backoff retries acknowledgement of the positive local delivered value, so a failed acknowledgement can recover without printing the message again. A fetched floor alone never advances local delivery or causes an acknowledgement; every ack is at or below local delivery. A gap fill fetches at most 20 rows per event; its continuation pointer says `up to <k> more in C<n>: pad chat show C<n> --since <seq>`, where k is the remaining seq span after the fetched page and may include the agent's own messages.

Idempotency uses only body `op_key` (at most 128 bytes), scoped to conversation and author pair, atomically in the store; there is no `Idempotency-Key` header alias. Repeating it returns the stored message and sequence regardless of replacement body, spends no sequence, and returns a tombstone if the original has since been deleted.

Limits are in-memory per server instance, in addition to the general API bucket. Agent send attempts spend from `ChatSend`, 20/minute with burst 20, keyed by conversation ID, user ID and agent key, after membership and JSON decoding. Human sends do not spend this bucket. Replays spend like other attempts; non-member requests create no bucket. Exhaustion is `429 rate_limited` with `Retry-After: 3` and `X-RateLimit-Limit: 20`. `POST /me/conversations` spends a `ChatDM` token only for a create, 30/hour per user with burst 30, with `Retry-After: 120` on exhaustion. Reusing an existing DM and invalid keys spend no token. Concurrent first creates that both pass the existence check may each spend a token. All 429 responses also carry `X-RateLimit-Remaining: 0`. The shared response helper reports `X-RateLimit-Limit` in requests per minute (so ChatDM reports `1`).

10. **Read-time visibility:** send accepts optional `context_workspace` as a workspace slug or ID. It is resolved for the caller with the token's workspace allow-list; unknown, soft-deleted and denied values all return byte-identical `400 validation_error`, `context workspace not found`, unless the `op_key` replays the caller's own prior message. The store additionally requires the author to be a workspace member. On messages-list and send responses, each message's `context_workspace: {slug, name}` is checked afresh for the reader and omitted entirely when no longer visible (including membership removal, soft deletion, token restrictions or a purged context). It is indistinguishable from a message that never had a context; the raw ID never appears. Deleted messages carry no context. The inbox's `last_message` stays excerpt-only without enrichment.

    Messages-list and send responses also carry page-level `refs: [Ref]`, always `[]` rather than `null` when empty. A `Ref` is `{workspace, ref, state, title?, collection_slug?}`. Non-deleted bodies contribute ref and workspace-ref wiki-links; title links and links inside code spans/fences are ignored. Bare `[[REF]]` uses that message's visible context workspace, or is `unresolved` without one. Entries are deduplicated across the response by workspace and canonical ref. `visible` adds the item's title and collection slug; `restricted` carries neither. Unknown workspace, unknown item and every denial yield byte-identical restricted entries apart from the workspace/ref strings already present in the body. At most 50 distinct refs are looked up per response; additional entries are `unresolved`, never `restricted`. The refs array contains at most 200 entries per response. Both messages-list and send responses always include `refs_truncated`, true when any distinct ref was dropped and false otherwise. A dropped ref has no entry and is rendered as plain text, which makes no claim about its visibility. Links open through `/-/r/{workspace}/{REF}`, which re-checks access on click.

11. **Quote excerpts:** `reply_to` passes through the store's first-line excerpt, at most 100 runes including a trailing `...` when truncated. It never contains the full quoted body. A deleted quote has `deleted: true` and an empty excerpt. Quotes are not scanned for refs.

12. **Effects:** chat emits no kernel event, activity row, outbox row or webhook. Its only bus effect is the ref-only `KindChat` watch notification (TASK-4041).

### Agent chat identity and arming

An agent gets a chat identity, and a roster entry on `/messages`, from a connected `pad watch --stream` carrying a non-empty agent name. Claude Code's `/pad:connect` arms the session first, then sets this up. Under another harness three things must hold:

1. **The session is armed.** `pad session arm` from the agent's session, or `[push] auto_arm = true` in the repo's `.pad.toml`; both are off by default, and an unarmed monitor exits at once (`runWatchMonitor` checks arming before anything else). An explicit `pad session disarm` overrides `auto_arm` and stops the monitor. An arm that cannot be verified on this platform fails closed (the monitor exits); `[push] auto_arm`, with no `pad session arm` file for the session, is the way to receive pushes there.
2. **The monitor runs from a directory linked to the workspace by `.pad.toml`.** Without the link the stream stays silent and retries hourly. The monitor is `pad watch --stream --for-session`, run by the harness as a background process alongside the agent, not by hand.
3. **The agent has a name.** `ResolveAgentName` resolves it in this order: registered name, then `agent_name` in `.pad.toml`, then `PAD_AGENT`; only Claude Code is detected without one. The registered name is this session's own live registry row (`pad session register --agent <name>`, which needs a verifiable owner pid); a row registered from an unrelated shell does not apply.

The web roster is built from the caller's own `GET /sessions` plus their existing DMs, so an agent with no name, or none connected, has no entry; the empty `/messages` page explains this only when both reads answered (a pending or failed list, or a `503` from `/sessions`, is unknown and never shown as "no agents"). An agent's own DM is `@<its-name>`: a name that differs from the caller's `X-Pad-Agent` is another agent's DM and is refused.

### Item commitments (TASK-4351)

Release note: `/commitment` replaces `/schedule`. The five old GET, POST, PATCH, DELETE and POST resolve routes now return 404. There are no aliases or compatibility routes.

The CLI is `pad remind` (`pad item remind` is the same command; `--start`/`--every` to schedule, and the `show`, `done` (`--at` records the actual completion time as `actual_done_at`), `skip`, `snooze`, `move`, `renegotiate` (a preview unless `--apply`; see "Commitment deadline renegotiation"), `link` (add/list/edit/rm), `gate` (add/list/rm), `agenda`, `edit` and `rm` subcommands; there is no `pad cal`); the MCP actions are `pad_item` `remind` (with `start`), `schedule`, `schedule-edit`, `schedule-delete`, `schedule-resolve` (with `actual_done_at`), `schedule-renegotiate`, `schedule-link`, `schedule-unlink`, `schedule-move` and `schedule-gate` (docs/mcp.md, v0.110), with commitment reads and resolves in the web client. One schedule per item; the schedule is the RULE, and its single outstanding occurrence is carried by a managed reminder row (`reminder_id`) that the reminder tick fires.

- `GET|POST|PATCH|DELETE /workspaces/{ws}/items/{ref}/commitment`. GET answers 200 (404 `not_found` "Schedule not found" when there is none) and, like the reminders list, reads an ARCHIVED item. POST answers 201 and `409 schedule_exists` when the item has one (PATCH changes it, DELETE removes it). PATCH answers 200. DELETE answers `{id, deleted: true}` and removes the managed reminder. POST, PATCH and DELETE need edit permission on the item (the reminders rule: viewers and `view`-grant guests get 403, a read-scoped token is refused, an archived item answers `409 archived`); an unknown or invisible item is 404. A POST, PATCH or resolve that races a move and finds the item archived under the write answers the same `409 archived` (the handler re-reads the item), 404 only when it is truly gone.
- **Bodies are strict.** A non-object body, unknown or repeated member, NUL, or wrong JSON type is `400 invalid_body`. On both POST and PATCH, `kind` and `dtend` are refused explicitly with `400 validation_error`, details `{field: "kind"|"dtend", code: "not_accepted"}`. POST requires `dtstart` and `roles`; optional timing members are `tz`, `floating`, `rrule`, `rdates`, `exdates`, `anchor`, `audience`, and `lead_minutes`. PATCH accepts those timing members, `dtstart`, and `roles`, all optional, with at least one required (`{}` is `400 validation_error`, code `required`). `rrule` accepts recurrence text or shorthand, not a separate `every` body member. `anchor` is `calendar | completion`, `audience` is `human | agent | both`, and `lead_minutes` is 0..44640. Walls (`dtstart`, `rdates`, `exdates`) are zone-less dates or `2026-11-02T09:00[:00]`. On PATCH, top-level `null` clears `rrule`, `rdates`, and `exdates`; other top-level members cannot be null. On POST, `roles` is the full object; an omitted deadline means no deadline. Its native offsets are: `target_days`, `target_secs`, optional paired `earliest_days`/`earliest_secs`, `deadline_days`/`deadline_secs` with `deadline_behavior: lapses|stays_owed`, `occupied_days`/`occupied_secs`, and `outcome`. On PATCH, `roles` is a partial object: an omitted member keeps its stored value, a value sets it, and `null` clears it where pairing allows. Clearing earliest or occupied requires both days and secs to be explicitly null; clearing deadline requires days, secs and behavior all null. Pairing is checked on the merged stored roles. `roles: {}` and `roles: null` are refused (`400 validation_error`, field `roles`, code `required`); null on either target member or on outcome is refused with `required` naming that member. A client that previously cleared a role by leaving it out of a replacement now keeps it and must explicitly clear its pair. Timing-only edits never convert legacy rows; naming at least one role member deliberately converts a legacy row to native. An unchanged partial writes no role columns, journal row or updated timestamp. The server maps no flags to roles.
- **Timing and roles are atomic.** PATCH reads and judges the whole request under one transaction lock. A native row already carrying a deadline refuses a changed canonical `dtstart`, `tz`, `floating`, `rrule`, `rdates`, `exdates`, or `anchor`, or a changed deadline offset/behavior, with `409 hard_deadline`, details `{field: "deadline", code: "combination"}`; use `POST .../commitment/renegotiate` with a reason. This applies to every caller, including owners and assignees, and to ended native deadline rows. No-op timing edits pass; audience and reminder lead edits pass. Legacy backfill rows retain their existing behavior. Adding a first deadline together with a timing edit passes; shifting the start while compensating a stored deadline offset is refused. Changing `lead_minutes` moves only the reminder.
- **Derived storage and labels.** A native roles write derives the stored label: a deadline takes precedence (`deadline_hard`, no stored end), else an occupied offset gives `window` and an end computed on the schedule's wall clock, else create gives `check` and an existing `check`/`deadline_soft` stays as it is (other labels become `check`). An occupied role is retained even beside a deadline. Zero or negative occupied offsets, out-of-range ends, and all-day starts with seconds in their occupied offset are `400 validation_error` on `occupied_until`, before writes. Start edits preserve the occupied offset on native and legacy windows. Roles reads remain authoritative; clients derive their label deadline first, then window, then check. Agenda and bootstrap also omit `kind`; their clients use the returned roles for labels. The stored column remains for activity metadata.
- **Zone default.** A POST naming neither `tz` nor `floating: true` is pinned to the caller's account zone (UTC when none is set, and then the response carries `timezone_note`). A PATCH of `floating: false` on a floating schedule with no `tz` does the same.
- **The view** is `{schedule_id, item_id, roles, occurrence_key?, journal, id, item_ref, dtstart, tz?, floating, rrule?, rdates, exdates, anchor, audience, lead_minutes, next_occurrence?: {at, wall}, next_override_at?, missed_count?, missed_truncated?, stale?, ended_at?, error_code?, reminder_id?, created_at, updated_at, timezone_note?}`. A pinned schedule's `next_occurrence.at` is the instant it fires for. An armed FLOATING schedule's is the `wall` read in the CALLER's zone (the tick uses the recipient's zone, so two callers may see different `at` for one `wall`); once a floating occurrence has fired, `next_occurrence.at` and a managed reminder's `occurrence_at` report the instant it fired for, whatever zone the reader or recipient is in now. `missed_count` is the occurrences that passed unresolved AFTER the outstanding one (which is not counted), computed on every read and never stored, at most 500 and looking at most 92 days past the outstanding occurrence; `missed_truncated` says the count is a floor; `stale` is `missed_count >= 2`. All three are omitted when there is nothing to report: an absent `missed_count` means 0, and an absent `missed_truncated` or `stale` means false. `next_occurrence` and `reminder_id` are absent once `ended_at` is set (a rule with nothing left, after an edit). `error_code` is null while healthy; it is set when the fire path could not advance a stored rule and cleared by a timing edit that compiles.
- **Errors.** `400 validation_error` with `details.code`: the ten schedule codes `syntax`, `unknown_part`, `duplicate_part`, `missing_part`, `range`, `combination`, `unsupported`, `unsatisfiable`, `zone`, `wall` (plus `part` and `value`, at most 64 bytes of the offending text); `cap_scan` and `cap_stall` (input-caused; separate codes); the store's `details: {field, code}` with `code` `enum`, `range`, `combination` or `required`, and on a resolve `format` (an instant member that does not parse); `never_occurs` (a POST, or a PATCH that names the rule, dtstart, rdates or exdates, whose rule plus RDATEs less EXDATEs has no occurrence at all from its dtstart: "this schedule never occurs", `details: {field: rrule|rdates, code: never_occurs}`; a rule whose occurrences have all passed is not this, and a PATCH that names none of those fields never runs the check); `floor` (TASK-4236: a schedule whose shortest gap between two consecutive fire instants, rule plus RDATEs, is under 15 minutes is refused on POST and on a PATCH that names the rule, dtstart, rdates or exdates (a tz, floating or anchor edit of an older row saves), with the message "schedules fire at most every 15 minutes" and `details: {field: rrule|rdates, code: floor}`; HOURLY and MINUTELY rules at or above 15 minutes are accepted, nothing is thinned, and schedules stored earlier and the agenda's display expansion are not limited by it; every RDATE is checked against its neighbours, and an RDATE the check cannot reach is never a pass: past the scan limit (a sub-daily rule with BYxxx lists and an RDATE more than about 3.8 years from dtstart) it is `400 cap_scan`, and when the check's shared work budget runs out it is `503 schedule_busy` with `Retry-After`, nothing written); `range` with `part: RDATE` or `EXDATE` for more than 1000 entries in either list; and `exhausted` (a POST whose rule has no occurrence at or after now; the same edit through PATCH ends the schedule instead, 200 with `ended_at`). A rule whose BYxxx lists multiply past the budget is `range` with `part: FREQ`. `cap_time` is `503 schedule_busy` with `Retry-After: 1` (load-dependent, retry). `cap_window` and `cap_instances` are never returned by a schedule write; `cap_instances` can appear only as a stored `error_code`, and `cap_window` is the agenda read's answer to a window over 92 days (see Workspace agenda). These names are API vocabulary and do not change spelling. Nothing is persisted on any refusal.
- **Resolving: `POST /workspaces/{ws}/items/{ref}/commitment/resolve`** (TASK-4103). Body `{occurrence_at, state, comment?, until?, actual_done_at?}`, strict like the others. `occurrence_at` is the RFC3339 instant of the outstanding occurrence as the caller last read it (the view's `next_occurrence.at`, or a reminder's `occurrence_at`), or a lapsed history occurrence for `done`. `state` is `done | skip | snooze | move`, `comment` is optional text written as an ordinary item comment in the same transaction, and `until` (RFC3339, after now and at most 366 days ahead) is required for `snooze` and `move` and refused for `done` and `skip`. A missing, mistyped or unparseable member is `400 validation_error` with `details: {field, code}`: `required`, `enum` (`state`), `format` (`occurrence_at` or `until` that is not an RFC3339 instant) or `range` (an `until` out of range) or `combination` (`until` on a done or skip). Permission is the PATCH rule (edit on the item; archived 409; unknown item 404; no schedule 404). Success is `200 {commitment: <the view>, resolution: {occurrence_at, state, comment_id?, missed_recorded}}`.
  - `done` and `skip` close the occurrence and arm the next one on the SAME managed reminder row (a fired row is re-armed; nothing is emitted by the resolve itself, so the next event is the next fire). A calendar schedule advances to the first instance after both now and the resolved occurrence, so resolving early does not return the occurrence just closed. Instances that passed unresolved after it become `missed` occurrence records (the same walk `missed_count` shows, so the count and the records agree; at most 500 records and 92 days past the occurrence, best-effort history). A schedule with nothing left (a one-shot, a rule past its UNTIL) is ended: `ended_at` is set and the managed reminder is removed.
  - **Lapsed history.** A `lapsed` occurrence is a closed history row for a hard deadline with behavior `lapses`, distinct from a cancel (`skipped`) and from the legacy `missed` state. On its tick, the deadline evaluator closes a due `lapses` occurrence itself with state `lapsed` and actor `system`; its `missed_recorded` journal row is the miss evidence and is retained. A recurring calendar schedule then arms the first instance strictly after the lapsed occurrence, even if its target time has passed. Each occurrence is judged against its own deadline: several due occurrences lapse in turn, each with its own miss evidence, up to 64 per schedule per pass; the next tick picks up any remaining due occurrences. A lapse writes no legacy `missed` occurrence rows. A completion-anchored schedule advances from the lapse time. A one-off ends when it lapses. A later `done` completes that history row with state `done` and the actual completion time (`actual_done_at`, or now when omitted), keeps the miss, and leaves the current occurrence and its reminder alone.
  - `snooze` keeps the occurrence outstanding and re-fires it once at `until`; `move` keeps it outstanding and makes `until` its new due instant (the lead is subtracted, so it fires `lead_minutes` earlier). Both re-arm the same managed row, leave `next_occurrence.wall` alone, report `next_override_at`, and fire an event whose `occurrence_at` is the ORIGINAL occurrence, and a second notification. A floating occurrence is frozen at the instant the caller named, so a later change of the recipient's zone does not move it. `next_override_at` for a snooze is `until` plus the lead (the stored value the fire instant is derived from). `move` also writes a `moved` occurrence record that the eventual done, skip or lapse replaces. A move on a NATIVE row that has a deadline role changes the target only: the deadline instant, the deadline evaluator and any recorded miss do not follow it, and a per-occurrence deadline override survives the move. A move that puts the target after the row's own deadline saves, and the response's `resolution` carries `warning: "target_after_deadline"`. On such a row `until` must be after now (a move into the past is `400 validation_error`, `details: {field: "until", code: "range"}`, as for snooze), since arming the next occurrence would otherwise drop this occurrence's deadline unrecorded. A LEGACY row (`roles_origin: legacy_backfill`) with a hard deadline cannot be moved (`400 combination` on `state`): nothing else enforces its deadline, and renegotiation refuses it too. The message names the way out: a `PATCH .../commitment` that names a role converts the row to native, after which the target can be moved.
  - **Skip and the deadline** (native rows with a deadline role; legacy rows are unchanged; `done` is unaffected). A skip cancels one occurrence, which is not a miss. (a) When the outstanding occurrence's deadline has already passed (the evaluator's own decision, a per-occurrence override counted) and its miss is not yet recorded, the skip records that miss FIRST, in the same transaction (an open item only; a closed item records none), so a skip never erases a miss that already happened. A miss already recorded stays, and adds no second. For a due `lapses` occurrence, the skip records the miss and then skips as usual, leaving state `skipped`. (b) A skip while that deadline is still ahead needs the renegotiate and DELETE authority (the item's assignee or a workspace owner; on an unassigned item any editor); no reason is required and the skip is journalled under the actor. Without it: `403 deadline_owner_required`, message "Only the assignee or a workspace owner can skip this occurrence before its hard deadline.", nothing written. An assignee that changed between the handler's read and the store's is `409 commitment_changed`. The checks run after the stale-occurrence match, so a stale client still gets `409 stale`.
  - **A moved or snoozed occurrence keeps counting the instances that pass while it waits.** `missed_count` walks from the occurrence's wall whatever the override: a daily occurrence moved three days out reads `missed_count: 3` (and `stale`) while it waits, and a later done records those three as `missed`. Snooze and move defer the occurrence; they do not move the schedule's grid. `next_occurrence.at` is the frozen instant for every reader, while the count is taken from the wall in each reader's zone. The `missed` records a resolve writes are walked in the RECIPIENT's zone (a floating schedule's), so for a reader in another zone `missed_count` can differ from the records by the instances that the zone offset moves across now.
  - **`anchor: completion`** means the next occurrence is one recurrence interval after the occurrence was DONE (resolved), not after it was due: the completion date in the schedule's zone (a floating schedule's recipient zone) plus the interval, at the schedule's time of day (an all-day schedule stays a date; HOURLY and MINUTELY are the completion moment plus the interval, to the second; the clock is cut to the second first). A month or year addition clamps to the end of the month (Jan 31 plus one month is Feb 28 or 29; Feb 29 plus one year is Feb 28). The result becomes the schedule's new start (for HOURLY and MINUTELY the grid starts at one of three instants, the first whose wall reads back to itself: the completion moment, else the completion moment plus the interval, else the completion moment minus the fewest whole intervals that make an hour. The engine reads a repeated fall-back wall as its earlier half, so the second half of a repeated hour cannot start a grid; every choice keeps the completion plus the interval on the grid, and the stored `anchor_wall` is that start's wall. If none could, which no real zone does, the schedule goes to its error state, `error_code` set and `409 schedule_error` on resolve, never a 500), an UNTIL still ends the schedule, and a wall in a spring-forward gap shifts forward. The next occurrence is always after the one resolved, so resolving early never re-arms the occurrence just closed. It is only valid for a plain interval rule (`FREQ` with `INTERVAL`, optionally `UNTIL`) or no rule at all (a one-shot, which done ends): a rule with a BYxxx part, a COUNT, RDATES or EXDATES under `anchor: completion` is `400 validation_error`, `details: {field: "anchor", code: "combination"}`, on POST and on a PATCH that changes the rule or the anchor.
  - **Stale and broken.** `409 stale` when `occurrence_at` is not the outstanding occurrence (already resolved or moved on, the schedule ended, or a floating one read in a zone that gives another instant), except for `done` on a lapsed history row: `details: {ended, next_occurrence?: {at, wall}}` carries the current one (a floating `at` in the caller's zone), so the caller can retry. An armed floating occurrence is accepted at the instant read in the recipient's zone or in the caller's own. Nothing is written. There is no idempotency key: a retried resolve that already took effect answers `409 stale`. `409 schedule_error` with `details.error_code` when the stored rule no longer compiles (nothing is advanced or ended; a timing PATCH repairs it). `cap_time` is the same `503 schedule_busy`.
- **Activity and events.** Each successful write logs `schedule_created`, `schedule_updated`, `schedule_deleted` or `schedule_resolved` (metadata holds the kind and, for an update, the member NAMES sent, and for a resolve the `state`; never rule text, walls, instants or comment text) and publishes `item_updated`. A resolve that sent a comment also publishes the ordinary comment event and watch notification. When the deadline evaluator closes a lapsing occurrence, it logs one `schedule_resolved` per schedule per pass with `state: lapsed` and actor and source `system`, and publishes `item_updated`.
- **Limitations.** (a) A FLOATING schedule with a bare HOURLY or MINUTELY rule cannot address the repeated hour of a fall-back; pinned schedules are exact. (b) Schedules travel with a workspace export/import, so `pad db migrate-to-pg` carries them (see "Schedules in a bundle" below), and a cross-workspace copy or move carries them armed fresh (see "Schedules on copy and move" under the copy endpoint), without the history and the snooze, reporting any schedule it skipped in `warnings.schedule.skipped`; a move refuses rather than end a live schedule it cannot carry. (c) A fired schedule fires once and then waits for a resolve: the managed reminder cannot be acked, so its reminder leaves the pending list when the schedule is resolved (a one-shot ends) or deleted. (d) `audience` routes the mobile push of a fire (TASK-4238): a fire of the schedule's managed reminder pushes to its recipient (the item's assignee, else its creator) only when `audience` is `human` or `both`; for `agent` no push is sent. The `item.reminder_due` outbox event is written for every audience, so webhooks and the agenda are unchanged. The audience is read at the fire, so a change applies from the next fire. A one-shot reminder has no audience and pushes as before. `audience` does not route events yet.
- **Schedules in a bundle** (TASK-4350). Workspace bundles always export version **4** (commitment gates and deleted blocker rows, below; version 3 introduced time links and version 2 introduced commitment members). Versions **1**, **2** and **3** still import, with no gates. Version **1** imports through the four-kind `legacyRoles` mapping (`legacy_backfill`), with occurrence actuals stamped `legacy_unknown`. A v1 bundle carrying any v2 member is refused. `WorkspaceExport.schedules` carries each live item's schedule with its resolved-occurrence history (`done | skipped | moved | missed | lapsed`) and its managed reminder's `remind_at`/`fired_at`. The optional v2 members are schedule `id` (source key only), `roles` (target, earliest, deadline and occupied offsets, deadline behavior, outcome and roles origin), `overrides` (occurrence key, role, value instant/wall and stored timestamps), occurrence `actual_done_at`/`actual_source`, and top-level `schedule_changes` (journal ids, item/commitment/occurrence references, type, role, before/after JSON, actor, reason/provenance, root/parent and recorded time). IDs and causal references are remapped; deleted-schedule journal rows survive while their item is live. `error_code` and the reminder's ack mark do not travel. The import re-compiles every rule through the create door and stores the CANONICAL timing, with `rdates`/`exdates` re-marshalled from the parsed walls (the bundle's text is never copied), rebuilds exactly one managed reminder per live schedule (none for an ended one), recomputes `next_at` and the reminder's fire instant from `next_wall`, the snooze override and the lead, and carries `next_wall`, `next_override_at`, `anchor_wall`, `ended_at` and the history (comment ids remapped to the imported comments). A schedule that fails validation (a rule that does not compile, an unknown zone, a bad enum, a malformed `rdates`/`exdates` entry, an inconsistent state) is DROPPED, COUNTED and REPORTED as `dropped_schedules: [{item, reason}]` on both import doors (and by `pad workspace import`); its item and the rest of the import are unaffected. `reason` is `<field>:<code>` (`rrule:...`, `tz:...`, `kind:...` and the other create-door field errors), `timing:<code>` for a rule or window the compiler refuses, or one of: `item:not_imported` (the item was not imported; `item` is then empty), `item:duplicate` (a second schedule for an item whose first was stored), `<field>:wall` / `<field>:instant` / `<field>:type` (an unparseable wall, instant or entry), `next_wall:required`, `next_wall:combination` and `anchor_wall:combination` (the all-day form disagrees with `dtstart`), `ended_at:combination`, `occurrence:duplicate`, `occurrence_state:enum`, `occurrence_actor:enum`, `occurrence_at:instant`, `resolved_at:instant`, `tz:zone`, or `invalid`. Role offsets must fit signed 32-bit integers; negative second offsets are supported. Commitment validation adds `roles:pairing`, `roles:enum`, `roles:range`, `override:duplicate`, `override:role`, `override:key`, `override:wall`, `override:instant`, `actual:combination` and `actual:instant`. An unparseable occurrence key drops the override or journal row; canonical keys use the destination schedule’s floating policy. Journal rows of absent or dropped items, dropped known schedules, mismatched item/commitment bindings, or invalid enums are folded into `dropped_schedules` with `changes:orphan`. An unknown source schedule with an imported item represents a deleted schedule and gets one new schedule identity. Milestone members (TASK-4358) are optional version 2 members on each schedule: `forecast` (`value`, `set_by`, `set_by_kind`, `set_at`, `source`), `forecast_events`, `children` (every selection row, active and removed: `item_id`, `kind`, `reason`, `added_*`, `removed_*`) and `completion_evidence`; a v1 bundle carrying any of them is refused. Import re-validates them with the write doors' canonicalisers and remaps child ids; a child whose item was not imported is dropped and reported in `dropped_schedules` as `children:orphan`, and an invalid member set as `forecast:invalid`, `forecast_events:invalid`, `children:invalid` or `completion_evidence:invalid`. Restore retains the journal and appends a system `import` marker. **Time links** (TASK-4353) are the version 3 member: top-level `schedule_links`, each `{parent_schedule_id, parent_role, child_schedule_id, child_role, offset, cancel_policy, created_at, updated_at, overrides}`, where the two ends are `schedules[].id` of the same bundle and `overrides` are the per-occurrence exceptions `{occurrence_key, offset?, no_longer_needed_at?, created_at, updated_at}`. Time links require at least version 3 because a reader that predates links ignores an unknown key and would restore the schedules without them; it refuses a version it does not know. A bundle of version 1 or 2 that carries `schedule_links` (even `null` or `[]`) is refused as a 400 (`export version N contains version 3 schedule members`); a version above 4 is refused as `unsupported export version`. Export writes a link only when BOTH its schedules are in the bundle (the schedule of a deleted item is not), so a link to one is left out and counted (`WorkspaceExport.OmittedScheduleLinks`, logged; it is not part of the bundle and names nothing); the bundle door is owner-only and unrestricted, so no link is filtered by reader. Import mints new link ids, remaps both ends through the schedule map, and re-checks each link as a live write does (role and policy enums, no self link, a valid offset held to what its columns store (`days` a 32-bit integer, `elapsed_secs` within 300 years, `clock_secs` within a day) that does not land outside 1970-2200 from the parent's date, read in the child's own zone too as the cascade does, both roles configured and a deadline only on native roles, one incoming edge per child role, no cycle, the 50-dependent and 16-hop limits, the 500-link component cap), all in the import's one transaction. It never moves a date and writes no cascade, no `move` journal row and no reminder: the bundle's dates are the truth. A link that fails is not imported, with its overrides, and is reported in `dropped_schedules` with `item` the link's child in the new workspace (empty when that item was not imported): `links:orphan` (an end is not a schedule of the bundle or was not imported), `links:enum`, `links:self`, `links:offset` (an unusable or out-of-range offset), `links:role` (a role the schedule does not have, or a deadline on legacy roles), `links:dates` (a schedule whose stored role data gives no readable date, such as an all-day schedule with a role 100,000 days before it: its links are dropped and the import goes on; a database fault still fails the import), `links:invalid` (an unparseable stamp), `links:duplicate_incoming`, `links:cycle` and `links:limit`. An import examines at most 10,000 links and a bounded sum of component sizes (about 2,000 checks of a full component, a few seconds); the links past either ceiling are left out and reported ONCE as `links:bundle_limit`, with no `item` and `count` set to how many were left out (an aggregate entry of `dropped_schedules` carries the optional `count`; an entry without one stands for one record). The derived-date range check applies only when both ends have an outstanding occurrence, as the cascade does. At most 10,000 override rows per link and 50,000 per import are examined; the rest are left out and reported once as `link_overrides:bundle_limit` with `count`. An override row that fails is dropped alone, the link kept; the first 100 are listed one by one and the rest are counted in one entry per reason with `count`, as `link_overrides:invalid` (a key that is not an occurrence key, an offset a link could not carry or that the parent's current date cannot take, neither an offset nor a mark, a bad stamp) or `link_overrides:duplicate` (two rows on one key after the child's floating policy is applied; the later edit is kept). A floating schedule is read in its recipient's zone, which is the item's assignee, else its creator; an import carries neither user id, so an imported floating schedule reads in UTC (and has no push recipient) until the item is assigned.

- **Commitment gates in a bundle** (version 4). Optional top-level `schedule_gates` carries `{id, blocked_item_id, blocker_item_id, blocker_schedule_id, blocker_occurrence_key, opened_at, created_at}`. `id` and the item and schedule references are source keys, remapped on import. `blocker_schedule_id` and `opened_at` are nullable; the captured occurrence key and opening timestamp are preserved exactly. Export includes every gate whose blocked item is live. When its blocker is soft-deleted, the bundle includes that blocker’s item row with `items[].deleted_at`, with an empty body and none of its schedules, comments, history or versions; the row takes no unique field value from a live item and does not count against the plan's item limit, and a row with `deleted_at` that blocks no gate in the bundle refuses the import; the gate carries a null blocker schedule and an empty occurrence key so it is judged by item status. Import preserves `deleted_at`, keeping the blocker absent from normal reads. Other deleted items and gates on deleted blocked items stay out of the bundle. Both items must import, a non-null schedule must import and belong to the blocker, and the graph must have no self gate, duplicate pair or cycle, and no item with more than 50 blockers. Invalid gates refuse the whole import with a validation error and roll it back; gates are never dropped as warnings. Import opens no gate and sends no notification. A version 1, 2 or 3 bundle containing `schedule_gates` or an item `deleted_at` member, including null or empty values, is refused as a 400 (`export version N contains version 4 schedule members`).

### Milestone forecasts and outcomes (TASK-4358)

A forecast is a hand-set estimate beside the commitment, not one of its roles; a milestone's outcome is derived on read from children selected explicitly. Both ride the commitment view: `forecast` (null when none) and `milestone` (always present).

- `PUT /workspaces/{ws}/items/{ref}/commitment/forecast` body `{value, source?}`: `value` is a date (`YYYY-MM-DD`) or an RFC3339 instant (stored in UTC); a value before now is allowed; `source` is at most 280 characters. It replaces the current forecast and appends a history event. `DELETE` on the same path clears it (a clear event) and answers 200 even when there was none. A forecast arms NO reminder, is never a missed deadline and needs no target. The view's `forecast` is `{value, set_by, set_by_name?, set_by_kind (user|agent), set_at, source, passed, history: [{action, value, prev_value, set_by, set_by_kind, source, recorded_at}]}`; `set_by_name` is the current setter name, omitted when unavailable; history events do not carry it. `passed` is derived for display on every read and never stored.
- `PUT /workspaces/{ws}/items/{ref}/commitment/children/{childRef}` body `{kind: "child"|"waiver", reason?}` selects a child (any item of the same workspace; no link is needed) or waives it; a waiver needs a non-empty `reason`. It is idempotent: selecting a selected child updates it. `DELETE` on the same path removes it softly (the row stays as history; removing a child that is not selected answers 200). Every write answers 200 with the commitment view and logs `schedule_updated` with the member NAME (`forecast` or `children`), never a value, reason or title.
- **Gates, in order:** the item (404, or 409 `archived`), edit permission (403), the schedule (404 "Schedule not found"), then the child. A child ref that does not exist, is in another workspace, is archived, or that the caller cannot read answers the same 404 `not_found` "Item not found", before any validation that could reveal it (kind, duplicate, cap). Selecting or removing a child needs read on the child and edit on the milestone.
- **Validation** is `400 validation_error` with `details: {field, code}`: `required` (`value`, `kind`), `format` (`value`; a NUL), `enum` (`kind`), `combination` (a waiver without `reason`; a milestone selecting itself, field `child`), `range` (`source` over 280 characters; `children` over 200 active selections). A cap refuses the request whole, names the cap in the message and never truncates; no count of children the caller cannot see appears. Bodies are strict (`400 invalid_body` for unknown members).
- **The `milestone` member** is `{children, counted, total, waivers, result, completed_at?, evidence_changed, changes, evidence, history}`. A child counts when its collection says it closed delivering (done minus `abandoned_options`; a value in the default `NegativeTerminals` fallback counts as abandoned until declared) or it carries a waiver. An abandoned, cancelled, open or archived child never counts. `result` is `completed` (every selected child counts), `pending`, `unknown`, or null with `total: 0` when nothing is selected. It is a reading: nothing resolves the occurrence or sets any item's status, and a reopened child makes the result `pending` again without touching the milestone.
- **Completion evidence.** When the milestone's occurrence is resolved `done`, the selection is snapshotted in the same transaction (child, kind, close state, done value). `evidence_changed` is true when the live selection now differs from the snapshot (a pending child that later succeeded, a removal, an addition, a later cancel) or a snapshot child went from a terminal to a non-terminal value after the snapshot (read from `status_transitions`, which item create, update, move and the fenced writers write, so a re-close still shows the reopen). Being pending at resolve does not set it. `changes` lists the differing children; `completed_at` is the latest done occurrence's completion time and is kept on a reopen.
- **Visibility.** Children are filtered for the reader, at read time, on the live selection, the history, the snapshot and every count. If any selected child (or any child of the latest snapshot) is one the caller cannot read, `result` is `unknown` and `evidence_changed` is null, whatever that child's state, and the hidden child's ref, kind and state appear nowhere; `total`, `counted`, `waivers` and the lists cover only children the caller can see. `unknown` therefore reveals that a hidden child exists; it reveals nothing else, and does not change when that child is reopened or closed. A selected child that is in the trash is judged by the same rule as a live one (the reader's access to its collection), reads as a visible child with close state `missing` that never counts, and can still be removed with `DELETE .../children/{ref}`; selecting a trashed child is a 404. A snapshot child that no longer exists at all cannot be shown to have been readable to the reader, so a reader-filtered read treats it as unreadable (`unknown`, `evidence_changed` null); an export keeps it.

### Commitment deadline renegotiation (TASK-4351)

`POST /workspaces/{ws}/items/{ref}/commitment/renegotiate` previews or applies a native deadline change. It uses the commitment mutators' visibility, archived-item, edit-permission and token-scope doors. An unknown or invisible item returns the same `404 not_found`. After those doors, the caller must be the item's assignee or a workspace owner; on an unassigned item, any caller with edit permission may act. This authority check runs before body decoding for every scope, including previews. The assignee used by a non-owner decision is rechecked under the transaction lock for renegotiation and native-deadline DELETE; a changed assignee returns `409 commitment_changed` without writes. Workspace owners do not depend on assignment. Refusal is `403 deadline_owner_required`, details `{field: "deadline", code: "authority"}`. DELETE through `/commitment` keeps the same authority restriction for a native deadline and names this route in its refusal: "to remove or change a hard deadline use POST .../commitment/renegotiate". Authorized callers may delete an unlinked schedule directly; a schedule without a deadline uses the ordinary DELETE permission.

The body is strict like schedule bodies: unknown or repeated members, non-objects, wrong types and NULs are `400 invalid_body`. Members are `reason`, `scope`, `deadline`, `deadline_offset`, `deadline_behavior`, `remove_deadline`, `revision`, `preview`, and `acknowledge_violations`.

- `reason` is required and must be non-blank after trimming, for preview and apply.
- `scope` defaults to `occurrence`. This scope needs `deadline`, an RFC3339 instant after now and within 366 days (validated after the override writer's rounding up to a whole second). It moves only the outstanding occurrence's deadline via an override. `remove_deadline: true` needs scope `series` (`400 validation_error`, field `scope`, code `combination`); offsets and behavior also need `series`.
- `scope: "series"` needs at least one of `deadline_offset: {deadline_days, deadline_secs}`, `deadline_behavior: "lapses" | "stays_owed"`, or `remove_deadline: true`. Offset members use the commitment roles input's field names and validation, including signed offsets. Both offset members must be supplied together. Behavior may change in either direction without changing the offset. An offset change that changes the effective outstanding deadline to at or before now is refused with `400 validation_error` (`deadline_offset:range`); behavior-only changes keep the current deadline, including when it has passed. Removal excludes offset and behavior; `deadline` is refused on series requests. Every scope requires a native row with a deadline and an outstanding occurrence; legacy or deadline-less rows return `400 validation_error`, code `combination`.
- An ended schedule has no outstanding occurrence, so both scopes, preview and apply, are refused with `400 validation_error`, details `{field: "schedule", code: "ended"}`, and nothing is stored. The check runs under the schedule lock after the authority test and before the revision comparison, so a preview taken before the schedule ended gets this answer on apply, not `commitment_changed`. A caller without authority still gets the `403 deadline_owner_required` and no notice.
- Series changes apply from the outstanding occurrence onward, including on a one-off schedule. Stored past occurrences, their overrides, and prior journal rows are preserved. An explicit deadline override on the outstanding occurrence is kept for offset or behavior changes; the preview reports this as `keeps_deadline_override`. Removal clears deadline offsets, behavior and the deadline override on the outstanding key; target and other roles stay. Role changes preserve the schedule trigger, managed reminder and snooze.
- If the old outstanding deadline already passed, its miss is recorded first in the same transaction using the evaluator's dedupe and conversion rules, even when the replacement deadline is in the future. Terminal items are skipped as in the evaluator. A later tick cannot record that old miss again. When the preview's occurrence is still outstanding, its deadline is due under the evaluator's conversion rules, and its behavior is `lapses`, apply records the miss only if it is not already recorded, commits the lapse, and returns `409 commitment_changed` (the `ErrCommitmentChanged` response, details `{field: "revision", code: "stale"}`) without applying the edit. The caller must preview again. A deadline that is not due or predates conversion does not trigger a lapse; a `stays_owed` occurrence accepts the edit normally and retains any recorded miss.

`preview: true` returns `200 {preview, revision}` and writes nothing. `preview` contains `scope`, `occurrence_key`, `applies_from` (the outstanding key), `current_deadline`, `new_deadline`, `current_deadline_behavior`, `new_deadline_behavior`, `current_offset`, `new_offset`, `miss_recorded_first`, `miss_occurrence_key`, `keeps_deadline_override`, and `clears_deadline_overrides`. Offsets are the base `{deadline_days, deadline_secs}` pair; an occurrence override changes the effective deadline without changing that pair. Removed values and an absent miss key are `null`. Preview and apply compute the same plan.

Apply requires the preview's opaque `revision` for both scopes (`400 validation_error`, details `{field: "revision", code: "required"}` when missing). The token hashes the schedule identity, updated timestamp and timing/outstanding state, all role columns, the outstanding key and deadline override value, the effective zone and the miss-first decision. A differing revision under the schedule lock returns `409 commitment_changed`, message "The commitment changed; re-preview before applying", details `{field: "revision", code: "stale"}`, with no writes. A deadline passing or its miss being recorded between preview and apply can therefore require another preview. A skip whose assignee snapshot went stale answers the same status, code and details with its own message ("The item's assignee changed while the skip was being checked; reload the occurrence and skip again").

Success apply returns `200` with the commitment roles and journal, as `GET .../commitment` does, and records `schedule_updated` activity with names-only metadata. Each renegotiation adds one user journal row with role `deadline`, acting user and trimmed reason: `move` for occurrence with `{deadline}` before/after values, `update` for series with `{deadline_days, deadline_secs, deadline_behavior}` before/after snapshots (all three null on removal). These snapshots contain no roles-origin or conversion marker.
  History also includes target, earliest and occupied-until moves, with additive `before_json` values. History and exported `schedule_changes` order by the parsed RFC3339Nano instant, then ID, so an exact second precedes its fractional instants. Variable-width stored stamps are preserved. Cross-item root and parent journal references are omitted when their item is unreadable. Dependent system reasons contain no parent text. The additive `conflicts` list reports the commitment own dates outside their bounds as `{role, bound, value, bound_value}`; it never names another item.


### Commitment graph access and refusals (TASK-4423)

Every commitment view, including GET and successful mutations, adds `links: []` and `gates: {state, gates: [], unresolved?}`. A link is `{id, parent_item_id, parent_role, child_item_id, child_role, offset, cancel_policy, created_at, updated_at}`. Roles are `target | earliest | deadline | occupied_until`; offsets are `{mode:"elapsed", elapsed_secs?}` or `{mode:"civil", days?, clock_secs?, all_day?, zone?}` (zero-valued members may be omitted). A gate is `{id, blocked_item_id, blocker_item_id, outcome, opened_at?, created_at}`; outcome is `pending | succeeded | cancelled | lapsed | skipped`. Gate state is `released | waiting | blocked_needs_decision`. A link or gate appears only when both items are live and readable. `unresolved` lists readable blockers only; gate state still reflects all blockers. `conflicts`, when present, lists only the item's own dates outside their bounds as `{role, bound, value, bound_value}`. No hidden item, title, identifier or hidden total is returned. Milestone children retain their separate including-trash visibility rule.

Linked renegotiation previews may add `cascade: {revision, changes, violations?, left_in_place?, renegotiates_deadline?}`. Each change is `{item_id, role, from?, to, root?}`; lists contain only readable items, with no count of the rest. Revision tokens are opaque, 43-character base64url strings. Apply refreshes permissions under the transaction lock. Set `acknowledge_violations:true` with the fresh preview revision to accept a readable dependent date crossing its own bound; the bound and link remain. Resolve accepts neither revisions nor acknowledgements.

Cross-workspace copy and copy-preflight use the same `warnings.schedule` report: `{carried, history_dropped, changes_dropped, forecast_dropped, children_dropped, links_dropped, gates_dropped, skipped?:{reason}}`. Both new counts are always present in a report and count only readable live link ends or blockers. A readable dropped gate produces this object with `carried:false` even without a schedule; a hidden-only gate produces no object. Links and gates remain workspace-local. A carried or imported journal row whose root or parent row stays behind masks its reason as `Date changed`, reason source and actor as `system`, matching an unreadable source lineage. Rows whose causal rows all travel retain their reason and actor.

Schedule PATCH/DELETE, resolve and renegotiate share these graph errors. Graph refusals contain no path, impact, observed count or limit. Field validation retains `400 validation_error` with only `{field,code}` details, including `reason`, `revision`, `role`, `to` and `cancel_policy`.

When any linked partner is unreadable or soft-deleted, `schedule_linked` has exactly this message, for either direction and any number of partners: "This date is linked to something you can't view. Ask a workspace owner to change or remove the link." A caller without edit authority over a changed hard deadline instead gets `deadline_approval_required`. Enqueue success, failure, dedupe and no recipient leave the refusal bytes identical. ### Commitment links, moves and gates

Let `W = /api/v1/workspaces/{slug}` and `C = W/items/{itemSlug}/commitment`. All routes use the workspace authentication, token-scope, workspace-access and rate-limit gates before any resource lookup. Item identifiers (`itemSlug`, `child`, `blocker`) accept the existing workspace-local slug, reference or UUID. Link and gate IDs are UUIDs; malformed IDs have the same answer as unknown IDs.

| Method and path | Request JSON | Success |
| --- | --- | --- |
| `GET C/links` | No body | `200 {links: Link[]}` |
| `POST C/links` | `{child, parent_role, child_role, offset, cancel_policy?, preview?, reason?, revision?, acknowledge_violations?}`; URL item is parent | Preview: `200 LinkWrite` with `link:null`; apply: `201 LinkWrite` |
| `PATCH W/commitment-links/{linkID}` | `{offset?, cancel_policy?, preview?, reason?, revision?, acknowledge_violations?}`; offset or cancel_policy required | `200 LinkWrite` |
| `DELETE W/commitment-links/{linkID}` | No body | `204`, empty body |
| `POST C/move-preview` | `{role, to, reason?}` | `200 Move`, no writes or notices |
| `POST C/move` | `{role, to, reason?, revision?, acknowledge_violations?}` | `200 Move` |
| `POST C/gates` | `{blocker}` | `201 Gate` |
| `DELETE W/commitment-gates/{gateID}` | No body | `204`, empty body |
| `GET C/gates` | No body | `200 GateView`, including an item with no schedule |

`Link` and `Gate` reuse the commitment view shapes above. `GateView` is `{state: "released"|"waiting"|"blocked_needs_decision", gates: Gate[], unresolved?: string[]}`. Its state accounts for all blockers; detail and unresolved IDs include only readable blockers. Reads never open gates or enqueue notices.

`Move` is `{revision, changes:[{item_id, role, from?, to, root?}], violations?:[same], left_in_place?:[same], renegotiates_deadline?:true}`. `LinkWrite` is `{link: Link|null, moved: Move}`. A link write plans the child's outstanding date using the parent's date and the offset, then cascades to linked dates. A cancel-policy-only update moves nothing. `cancel_policy` defaults to `waiting_on`; `cancel_child_occurrence` is the other value. Roles are `target | earliest | deadline | occupied_until`; `to` is an RFC3339 instant.

Request offsets are a strict union: `{mode:"elapsed", elapsed_secs}` or `{mode:"civil", days, clock_secs, all_day, zone}`. Supply every member of the selected mode, including zero or false. Members of the other mode are a `combination` error even when zero. Elapsed seconds are integers within ±(300 × 366 × 86400); civil days are signed 32-bit integers, clock seconds are 0–86399, and zone is a pinned IANA zone (never `Local`). All-day offsets require a zero clock. Response offsets may omit zero-valued members, as in the commitment view.

Bodies are strict: unknown or repeated members, wrong JSON types, non-object bodies and NULs return `400 invalid_body`. Field errors return `400 validation_error` with details containing only `{field,code}`, where code is `required | enum | format | range | combination`. Required fields include child, blocker, parent_role, child_role, offset, role and to. Reasons are required when a move changes a hard deadline. A move that changes a hard deadline or crosses a readable dependent bound needs the fresh preview revision; bound crossings also require `acknowledge_violations:true`. Cheap moves may omit revision. Revisions are opaque 43-character unpadded base64url tokens; retain and return them without decoding or deriving meaning from them.

Both ends must be readable before edit, duplicate, cycle or limit errors are reported, and both must be editable to create, update or delete a link or gate. Every mutation reloads access in its own transaction after pinning; a preview does not authorize its commit. Direct moves of the root's own deadline also require the renegotiation authority and assignee guard. Dependent deadlines require edit authority on those dependents.

Missing, unreadable, soft-deleted, foreign-workspace and disappearing resources all return `404` with the same body: `{"error":{"code":"schedule_link_not_found","message":"Commitment link or gate not found"}}`. Missing deletes also return this 404. For the two deletes only, workspace owners (by workspace owner ID or membership role `owner`, never an app principal) may remove links and gates across collection restrictions and soft-deleted ends, including a deleted parent. This removal exception grants no live-mode access to deleted items.

Link and gate detail is visible only when both ends are readable. Move changes, violations and left-in-place entries are filtered to readable items, with no count of hidden entries. The hidden-partner sentence remains: “This date is linked to something you can't view. Ask a workspace owner to change or remove the link.” For anyone but a workspace owner, one or several hidden or deleted partners produce identical refusals. A workspace owner reads the graph through their own collection access like any member; only removal reaches past it and onto deleted ends, so the owner's refusal offers removal of the hidden links (see `schedule_linked` above).

### Workspace agenda (TASK-4104)

Outstanding schedule entries and admitted priority/waiting rows may carry `forecast: {value, set_by, set_by_name?, set_by_kind, set_at, source}`. This display summary has no `passed` or `history`. Forecasts never admit additional items, alter paging, arm reminders or produce overdue/miss state; only an explicitly hand-set forecast is shown.

`GET /workspaces/{ws}/agenda?from=<RFC3339>&to=<RFC3339>&tz=<IANA>`: the schedules' occurrences and the items dated inside the window, in one list. The CLI renders it as `pad item remind agenda`; the MCP action is `pad_item` `agenda` (docs/mcp.md, v0.107). Open to every principal `RequireWorkspaceAccess` admits.

- **Window.** `from` and `to` are required RFC 3339 instants with `to` after `from` and at most 92 days apart (92 exactly is allowed). `400 validation_error` with `details`: `{field: from|to, code: required|format}`, `{field: to, code: range}` for `to <= from`, `{code: cap_window, limit_days: 92}` for a longer window. `tz` is optional: an IANA name that decides how a FLOATING schedule is read and how `at` and `day` are rendered (`400 invalid_tz`, `Local` included). Absent, the caller's account zone is used, else UTC with a `timezone_note`. `tz` never moves a pinned instant.
- **Visibility** is the dashboard's: the caller's visible collections plus their item grants, applied in SQL before any bound, so items they cannot see never push a visible one past a limit and never appear in `entries`, `truncated` or `unavailable`. Terminal items contribute recorded commitment history only: no recurrence projections, target-passed, derived missed or overdue state. Dated fields remain limited to non-terminal items.
- **Response.** `{from, to, tz, timezone_note?, entries, window_complete, priority_list, priority_list_complete, waiting_on, waiting_on_complete, no_date, no_date_complete, no_date_scope?, truncated?, next_from?, unexpanded?: [{schedule_id, item_ref, item_title, collection, audience, reason}], unavailable?: [{item_ref, code}]}`. Entries are ordered by `at`, then schedule before date, then `item_ref`, then `schedule_id`/`field`. `at` is RFC 3339 in `tz`'s offset and `day` its local date (an all-day entry's `day` is its date, not shifted by `tz`).
  - **Schedule entry:** `{type: "schedule", at, day, wall, all_day?, floating, state, item_ref, item_title, collection, roles, occurrence_key, roles_origin, audience, schedule_id, fired?, overdue?, resolved_at?, actor?, comment_id?, missed_count?, stale?}`. `roles_origin` is `native` or `legacy_backfill`; a legacy row with a hard deadline refuses a move (see `move` above). `roles` is the effective `{target, earliest, deadline, deadline_behavior, occupied_until, outcome, roles_origin}` object from the commitment contract (absent roles are null). `occurrence_key` and `wall` identify the immutable recurrence seed; `at` is the effective target instant (local midnight for an all-day target). Every occurrence appears once, with all its roles, when **any** role falls in `[from,to)`, including roles outside the window on that same entry. `state` is `outstanding` (the one live occurrence; carries `fired`, `overdue` once due, `missed_count`, `stale`), `done | skipped | moved | missed | lapsed` from the history row, `missed` also derived for a passed instance with no row (the rule `missed_count` uses), `scheduled` (future), or `unrecorded` (before the outstanding occurrence with no row; a state is never invented). A moved occurrence is placed only at its effective target: moving into the window admits it, moving out removes its original placement (unless another effective role is in the window). Previous dates are available in commitment `journal`, never as a second live entry. A snooze changes reminder timing only.
  - **Matching history to occurrences** is by the WALL for floating and all-day schedules (a resolve stores the recipient's reading, which is another instant in the caller's zone) and by the INSTANT for pinned timed ones.
  - **Date entry:** `{type: "date", at, day, field, date, overdue?, item_ref, item_title, collection}` for `due_date` and `end_date` (the same keys `overdue` uses), one per hit. `date` echoes the stored value (`YYYY-MM-DD` or RFC 3339); `day` is its own first ten characters. An entry is SELECTED by its calendar day in `tz` (the window's first and last local days), not by instant. `at` is local midnight of that day for a date-only value and the stored instant for a datetime value, so `at` may fall outside `[from, to)` (a date-only item on `from`'s day, or a datetime on the window's last day after `to`). `overdue` is the stored value before the caller's today. An item dated before `from`'s day is not listed.
- **Bounds, never a 400.** A schedule that cannot be read (a stored `error_code`, a rule that no longer compiles, stored state that will not parse) is listed under `unavailable` with its code and the response is still 200. A schedule whose rule cannot be walked to the window inside the scan limit (such as a minute-level rule with a dtstart decades back) is listed under `unexpanded` instead, with `reason: "scan_limit"` (the only value), and the response is still 200 and `truncated`. A time or stall cap that examined nothing in the window stays under `unavailable` (`cap_time`, `cap_stall`), also `truncated`, and with no `next_from`. One schedule shows at most 100 entries (`truncated`), the response at most 500, at most 1000 schedules are read and expansion stops after 1.5 s (`truncated`).
- **Truncation and `next_from`** (TASK-4236). A cap hit inside the window is a truncated 200, never an error; a window longer than 92 days stays a 400. `next_from` (RFC 3339, UTC) is present only when every cut that fired is ordered by time: the per-schedule cut, the response cut, the 500-instance cap, and a time or stall cap that examined part of the window. It promises that every instant BEFORE it was examined and the entries shown are those before it; page by repeating the request with `from=<next_from>`. It is inclusive, so an entry at `next_from` itself may repeat: dedupe on `schedule_id` and `occurrence_key`. A schedule named in `unexpanded` is the exception to that promise: nothing of it was examined, whatever `next_from` says. When it is the only cut, `next_from` equals `to`. A cut on a dated entry (selected by calendar day, not by instant) carries no `next_from`, and `next_from` is always after `from` and no later than `to` (equal to `to` means the window was read to its end; page with a later `to`). When any cut that is not ordered by time fired (more than 1000 schedules, the 1.5 s budget, the dated half cut), `truncated` is true and `next_from` is absent whatever else fired: narrow the window or filter by collection. There is no schedule cursor.
- **Incomplete lists.** `truncated` means the list is incomplete: narrow the window. The dated half is cut at 501 items BEFORE date ordering, so past 500 dated items a later date can be shown while an earlier one is missing. More than 1000 live, visible schedules still truncate the schedule scan by id; schedules that ended before `from`, with no history near the window, do not count toward the 1000. A schedule whose stored state cannot be read is listed under `unavailable` with code `internal` (logged by id and error class only) and the response is still 200.
- **History before the anchor; dense rules.** Rows before a schedule's `anchor_wall` are listed from history only (the rule is not walked there). `unrecorded` is derived only from `anchor_wall` on; earlier instances without a row are not invented. The 100-entry cap per schedule applies to the window's first 100, so a dense rule shows its earliest occurrences.
- **Actionable groups (TASK-4354).** `priority_list`, `waiting_on`, and `no_date` are always arrays. They use the same live, non-terminal item visibility as the chronological window, independently of that window's dates and truncation. `priority_list` contains one outstanding occurrence per placed, unblocked commitment, including future targets, passed targets and still-owed deadlines. Rows carry the schedule entry's own `roles` and identity, plus `rank: high|normal|low|unranked` and `reason: outstanding|target_passed|deadline_still_owed`. Rank is read from a collection's declared `priority` select field only when the actual value is among its options: `critical`/`high` map to high, `medium`/`normal` to normal, `low` to low (case-insensitive recognized words). Missing, undeclared or arbitrary options, including convention priorities, are unranked. Options are never assigned meaning by their position. Reference collections (`tracks_work:false`) contribute only explicitly attached commitments or gates; their otherwise undated documents are not unplaced work. Within a rank the server orders by hard deadline (absent last), target (absent last), then immutable item ID. No Needs score is used.
- **Workspace No date scope.** Without `recipient=<user ID>`, the workspace agenda returns `no_date: []` and `no_date_scope: "personal_only"`. The marker means **not listed here**, never "nothing undated". Unfiltered work scans select only items with a schedule or gate; unscheduled open work does not consume the scan cap. With a recipient, actionable groups use the item's assignee, else creator, and schedules include the caller's human/agent audience; `no_date` is listed and `no_date_scope` is omitted. `GET /me/agenda` lists the caller's own work across admitted workspaces and also omits the marker.
- **Unplaced and blocked work.** An open work item without a commitment target is in `no_date`, with `reason: unplaced`; an item held by commitment gates is in `waiting_on`, with `reason: waiting|blocked_needs_decision`, even when it has a suspended schedule. A waiting row with an outstanding schedule also carries its own effective `roles`, `schedule_id`, and `occurrence_key`, with no calendar placement. These rows are `{type: "item", item_ref, item_title, collection, reason}` with workspace labels on `/me/agenda`; they carry no `at` or `day`. Blocked work appears in neither chronological date/schedule entries nor priority. Agenda groups deliberately omit all graph-end detail; `/commitment` retains the read-both-ends filtering below. No hidden ref, role, offset or derived parent date appears in an agenda group.
- **Independent completeness.** `window_complete`, `priority_list_complete`, `waiting_on_complete`, and `no_date_complete` are always booleans. False means the section cannot be read as an empty or complete total, even with an empty array. The chronological caps remain 100 occurrences per commitment, 500 entries and 1000 schedules per request. The actionable read independently admits at most 1000 visible open items across admitted workspaces, before classification, and caps each output group at 500; a scan or budget cut makes all affected groups incomplete, while a group's output cap changes only its own flag. Stored unreadable commitments also make priority incomplete. A group-read error preserves the chronological window and marks the groups incomplete; a per-item gate-read error makes only `waiting_on_complete` false and the read continues. The actionable read never sorts or relies on the truncated window. The 1.5-second request budget applies to both reads. Multi-role candidate windows share the existing seed expander and caps; a cut without an authoritative effective-time resume point has no `next_from`. `unavailable` makes `window_complete` false. UI consumers must state incompleteness instead of claiming there is no work.
- Never in the response: item content, comments, rule text, `next_at`, `kind`, `effective_at`.

### Saved views and the calendar (TASK-4239)

Outstanding schedule entries and admitted priority/waiting rows may carry `forecast: {value, set_by, set_by_name?, set_by_kind, set_at, source}`. This display summary has no `passed` or `history`. Forecasts never admit additional items, alter paging, arm reminders or produce overdue/miss state; only an explicitly hand-set forecast is shown.

**Views.** `POST /workspaces/{ws}/collections/{coll}/views` and `PATCH .../views/{id}` take `view_type` as a free string (no allow-list) and a `config` object. Only `view_type: "calendar"` is checked, on create and on the MERGED result of a PATCH that sends `view_type` or `config` (a rename alone is not re-checked, so a calendar whose field was later removed from the schema can still be renamed or switched to another type). The check runs after the reserved `$unparented` filter is stripped. `config.date_field` is required: a date field of the collection, or the built-in `created` or `completed`. `config.end_field` is optional: a date field of the collection only. The built-ins `created` and `completed` are refused as `end_field` whatever the schema declares, even a date field of that name (`400`, code `builtin_end_field`); as `date_field` a same-named schema field is shadowed by the built-in. Refusals are `400 validation_error` with `details: {field: date_field|end_field|config, code: required|unknown_field|not_date|unsupported_field_key|builtin_end_field|config}`; the message names the field. `unsupported_field_key` refuses a declared date field whose key has a character outside letters, digits, `_` and `-` (for example `start date`): the item store cannot read such a key, so a calendar on it would show nothing. The same check runs on the calendar route's `date_field` and `end_field`. A collection whose stored schema cannot be parsed answers `500`, not a `400` about the field. A calendar view belongs to a collection. A share link shows a calendar view to its readers as `view_type: "list"`; the calendar route is not a share route.

**Calendar read.** `GET /workspaces/{ws}/collections/{coll}/calendar?date_field=&end_field=&from=&to=&tz=` plus any item-list filter parameter. No saved view is needed (a saved calendar view supplies `date_field` and `end_field` to the client). Anyone who may read the collection's item list may call it, viewers included, and a collection the caller cannot see answers byte for byte as the item list does (`404 not_found`, before any parameter is read). The path collection narrows the caller's scope and never widens it: an item-grant guest sees only the granted items of the collection and their schedules.

- **Window and zone** are the agenda's: `from` and `to` required RFC 3339 instants, at most 92 days apart (`400 cap_window` beyond, same details), `tz` an IANA name. `date_field` and `end_field` are checked by the view check above; a stale or unknown field is `400` naming it (the web shows that as a prompt to pick another field, never as an empty month).
- **Filters.** The item list's own parameters (`status=open`, `tag`, `search`, `assigned_user_id`, `parent` ...) go through the item list's parsing and key check, so an unknown filter key is the list's `400 invalid list filter`. `limit`, `offset`, `sort`, `group_by`, `include_archived` and `non_terminal` are ignored. Schedule entries follow the items the filters select: with a filter active, the schedules read (the agenda's, scoped to this collection and the caller, at most 1000) are kept only when their item passes the filter, and the item need not have its date in the window. Past 1000 schedules a filtered calendar can show fewer entries; it reports `truncated`.
- **Items.** Terminal (done) items are included; archived and deleted ones are not. Content is not carried. `items` is `[{item, day, end_day?}]`: `item` is the item-list projection, `day` the viewer's day it is placed on, `end_day` the last day of a span. A date field places an item on its stored value's first ten characters (a date stays on its date; an RFC 3339 value keeps its OWN offset, so `2026-11-02T23:30:00-08:00` is 2026-11-02). `created` and `completed` are instants and are placed on the viewer's day in `tz`. `completed` is the latest move into a positive terminal status (the collection's terminal options minus its abandoned ones) of an item that is still in one; abandoned, reopened and never-moved items are not plotted. With `end_field`, items whose `date_field <= to` and `end_field >= from` are also selected; an empty `end_field` value or one before the start is a single day on `date_field`. A value that is not a date places no item.
- **Entries** are the agenda's schedule entries (same shape and bounds, `unexpanded`, `unavailable`), computed after scoping. An open item's entries are the agenda's. A terminal item (done or abandoned) shows only the entries with a recorded state (`done`, `skipped`, `moved`, `missed`, `lapsed`), never an `outstanding`, `scheduled`, `unrecorded` or overdue one, so a finished item never says work is left. The workspace and personal agendas share this terminal-history behavior.
- **One cap.** At most 500 items plus schedule entries together, selected in day order and cut only between days. `truncated` is set when anything is left out; `next_from` (`YYYY-MM-DD`, the viewer's day) is the first day not shown, nothing at or after it is in the response, and asking again from the start of that day returns the rest. "No gap and no repeat" holds for items whose start day is in the window; a span that began before `from` is selected by overlap on every page it overlaps and is returned each time with its original `day` (the renderer needs it), counted against the cap each time. Within a day: items first, by the value's own text then id, then entries by instant, item ref, schedule. If the first day alone is over the cap, 500 of it are shown, `partial_day` names that day, `truncated` stays set and `next_from` is the next day (absent when that is past `to`); the rest of that day cannot be paged to, so filter the calendar or use the list. If carried-in spans alone fill the cap on the first day, that is the first-day case above and `next_from` moves on, so paging always advances and ends. A cut by an unordered schedule limit (scan, time budget) promises no `next_from`, and a time-bounded cut on the first day reports `truncated` with no `next_from`, even when the day cap also cut. `partial_day` is only ever a day that is shown: when a schedule's time cut pulls `next_from` back to it or before it, it is absent. A schedule that is finished and fires more often than its 100-entry cap covers contributes its earliest occurrences, as in the agenda, so recorded entries later in the window can fall past the cap; `truncated` is set. Items are read in date order in SQL for every key (`completed` by the instant of the move, a date field by its first ten characters), so the read stops once the cap is in hand.
- **Names.** A schema date field literally named `created` or `completed` is shadowed by the built-in of that name. Items carry no `content` on the calendar, with or without `search`. The route's own parameters (`from`, `to`, `tz`, `date_field`, `end_field`) are not item-list filters here, so a collection field with one of those names cannot be filtered on in the calendar. A saved calendar view created outside these handlers (an import, an app) is not checked at write time; the route validates `date_field` and `end_field` on every read, so a stored config naming a field that no longer exists answers `400` naming it. A PATCH of a calendar view whose collection is deleted answers `404 not_found` (`View not found`).
- **Response.** `{from, to, tz, timezone_note?, items, entries, truncated?, next_from?, partial_day?, unexpanded?, unavailable?}`.
- **FieldRanges** (store, `models.ItemListParams`): per-range `substr(value, 1, 10) BETWEEN from AND to`, ANDed; `to` is an inclusive day. A key is accepted only if it is letters, digits, `_` or `-` (checked in the store); any other key matches nothing.

### Personal workspace groups (TASK-4243)

Groups are private per-user workspace filters. They never grant access. These user-scoped routes sit outside the workspace access subrouter and are available through the REST API and web client only. A token pinned to one workspace is refused on all five routes with `403 token_workspace_pinned`: group names are free text and a group spans workspaces.

- `GET /api/v1/me/workspace-groups` returns `200 {groups: [...]}`: computed `all` and `mine`, followed by named groups ordered by the byte order of the lower-cased name (Go `strings.ToLower`, the same on SQLite and Postgres), then id.
- `POST /api/v1/me/workspace-groups` takes `{name, workspace_ids}` and returns the created named group with `201`.
- `GET /api/v1/me/workspace-groups/{id}` returns one entry with `200`. The ids `all` and `mine` also work here.
- `PATCH /api/v1/me/workspace-groups/{id}` takes any subset of `{name, workspace_ids}` and returns the updated entry with `200`. Members replace the list the caller can see; saved members the caller cannot see right now (access lost) stay, and count toward the 100 cap. `{}` is a no-op.
- `DELETE /api/v1/me/workspace-groups/{id}` returns `200 {id, deleted: true}`.

Each entry is `{id, name, kind: "all"|"mine"|"named", workspace_ids: [...]}`; named entries also include `created_at` and `updated_at`. Member ids are ordered by workspace slug, then id. `all` is named `All workspaces` and contains every currently admitted workspace. `mine` is named `My workspaces` and contains only admitted workspaces owned by the caller. Both are computed on every request, never saved. PATCH and DELETE on either return `400 validation_error`, details `{field: "id", code: "builtin_group"}`.

Every response intersects saved members with the current admission set used by `/me/needs`: live membership and guest workspaces, narrowed by token consent and a single-workspace token pin. Revoked, deleted or token-excluded members disappear silently, with no id, name, slug, count or error. An empty named group remains visible. Another user's group id and an unknown id produce byte-identical `404 not_found` responses on GET, PATCH and DELETE. App principals receive the same `404 not_found` as `/me/needs` before processing parameters; an unauthenticated caller receives `401 unauthorized`.

Saves are all-or-nothing. A `workspace_ids` member must be a currently admitted workspace UUID, not a slug. Unknown, deleted, inaccessible and token-excluded ids all receive the same `400 validation_error`, details `{field: "workspace_ids", code: "unknown_workspace"}`, without echoing any id. Duplicate ids collapse silently; an empty array is allowed. Membership is checked again when responding and on every subsequent read.

Limits are 20 named groups per user, 100 distinct workspaces per group, and names of 1–60 Unicode runes after trimming surrounding whitespace, without control characters. Violations return `400 validation_error`, details `{field: "groups"|"workspace_ids"|"name", code: "range"}`. Names are unique per user case-insensitively: a collision returns `409 conflict`, details `{field: "name", code: "name_taken"}`. Keeping or changing the case of the group's own name is allowed. Names `all` and `mine` in any case are reserved (`400 validation_error`, details `{field: "name", code: "reserved"}`). The group cap and name check run under a per-user write lock.

Bodies are strict, as for schedules: non-objects (including top-level `null`), unknown or repeated members, wrong JSON types and a NUL anywhere return `400 invalid_body`. Both POST members are required. An explicit `null` member on POST or PATCH returns `400 validation_error`, details `{field, code: "required"}`; omit a PATCH member to leave it unchanged. Null array elements are an invalid type.

### Personal agenda (TASK-4241)

Outstanding schedule entries and admitted priority/waiting rows may carry `forecast: {value, set_by, set_by_name?, set_by_kind, set_at, source}`. This display summary has no `passed` or `history`. Forecasts never admit additional items, alter paging, arm reminders or produce overdue/miss state; only an explicitly hand-set forecast is shown.

`GET /api/v1/me/agenda?from=<RFC3339>&to=<RFC3339>&tz=<IANA>&group=<all|mine|id>` is the cross-workspace agenda feed for the web client. It includes membership and guest workspaces, honours the token consent allowlist and a single-workspace token pin, and applies the same per-workspace visibility as `/me/needs` (the backlinks visibility rule, which leaves system collections out for a restricted member; the workspace agenda reads visibility through the dashboard rule instead, so the two can differ for such a member). Schedule and date entries are read in any live collection the caller may see; `created` and `completed` entries only in non-system ones. Lost, unknown and token-excluded workspaces contribute nothing: no entry, count, unavailable or unexpanded row. No admitted workspaces returns the same `200` with `entries: []` as admitted workspaces with no entries. An app principal receives `404 not_found` before parameter processing, byte-identical to `/me/needs`; no signed-in user receives `401 unauthorized`.

- **Parameters.** `from` and `to` are required RFC 3339 instants, with `to > from` and at most 92 days between them. The workspace agenda's refusals apply: `400 validation_error` with `details.field: from|to` and `details.code: required|format`, `field: to, code: range` for an invalid interval, or `code: cap_window, limit_days: 92`. Optional `tz` overrides the stored user zone; invalid or empty values receive `400 invalid_tz`. Without `tz`, an unset user zone defaults to UTC with `timezone_note`. Optional `group` narrows the workspaces to `all` (the default), `mine` (workspaces the caller owns) or the id of one of the caller's saved workspace groups; the entries and the counts both follow it. Another user's group id and an unknown id are the same `404 not_found` as on the group routes, and a group never reaches a workspace the caller could not already read. An empty value is `400 validation_error` with `details.field: group`. A token pinned to one workspace that sends `group` at all (its own group id, an unknown id, `all` or `mine`) receives `403 permission_denied` with `details.reason: token_workspace_pinned`, decided before any group is looked up, so the answer says nothing about which ids exist; without `group` a pinned token sees only its own workspace, in the entries and in `counts`.
- **Response.** The workspace agenda's `{from, to, tz, timezone_note?, entries, window_complete, priority_list, priority_list_complete, waiting_on, waiting_on_complete, no_date, no_date_complete, truncated?, next_from?, unavailable?, unexpanded?}` shape, plus `counts` and `counts_truncated?` (below). Every chronological and grouped entry also has `workspace` (slug), `workspace_name` and `owner_username` (slugs are unique per owner, so two admitted workspaces can share one); every unavailable and unexpanded row carries `workspace` and `owner_username`. Schedule and date entries retain the workspace agenda semantics, including the wall date for an all-day entry's `day`.
- **Personal groups.** `priority_list`, `waiting_on`, and `no_date` contain the caller's own work: items assigned to the caller, or created by the caller when nobody is assigned. Schedules must include the caller's human or agent audience, exactly as in bootstrap. The All / Mine / named workspace-group picker only chooses admitted workspaces; it does not broaden personal group ownership. Chronological entries and counts retain their workspace visibility scope.
- **Item events.** `created` and `completed` entries contain `{type, at, day, item_ref, item_title, collection, workspace, workspace_name, owner_username}`. Creation uses `items.created_at` in `[from, to)`. Completion uses the latest in-window positive-terminal status transition per item (terminal minus abandoned). Both join live items in live, non-system collections and apply current item visibility; an item moved out of scope or deleted does not appear. Their `day` is the viewer-local date of `at`.
- **Counts.** `counts` is one `{day, completed, open, burndown}` per viewer-local day the window touches (the first and last day are partial when the window is not day-aligned; events outside `[from, to)` are not counted). `completed` is the items that reached a positive terminal value that day (terminal minus abandoned), each item once per day. `open` is the items not at a terminal value at the day's end, or at `to` for the last day. `burndown` is how many of the items open at `from` are still open at the day's end; items created later never add to it, and there is no ideal line. Counts come from the same visibility-filtered item set as the entries (live items in live, non-system collections the caller may read), never from workspace totals, so a hidden item moves no number. Admitted workspaces with nothing give zeros, one object per day. Reading is bounded by the window maximum and by 20000 item creations and status changes per request; a request that would read more sets `counts_truncated` and `truncated`, omits `counts` (a partial series would read as a total) and omits `next_from`.
- **Ordering.** Instant, then type (`schedule`, `date`, `created`, `completed`), then workspace slug, item reference, and schedule id/field/item id. Workspaces are processed in slug order so a scan or budget cut is deterministic. The chronological windows, counts and item events run across all admitted workspaces before actionable groups run workspace by workspace on the remaining shared deadline. A deadline cut during the group pass lowers only group completeness; it does not change `window_complete`.
- **Bounds.** One request-wide limit of 500 entries after merging and sorting, 1000 schedules scanned across all workspaces, and a 1.5-second budget. The workspace agenda's expansion bounds also apply, including 100 entries per schedule. Each workspace's dated, created and completed halves reads at most 501 items in SQL; created and completed rows are ordered by time and id before that bound. Each overflowing half sets `truncated`.
- **Truncation and resuming.** The workspace agenda's inclusive `next_from` contract applies. A time-ordered cut on a schedule, created or completed entry resumes at the first unshown instant; repeat with `from=<next_from>`. Entries tied at that instant may repeat, so deduplicate them. A cut on a date entry, an overflowing dated/created/completed half, the request-wide schedule scan cap or the budget sets `truncated` and omits `next_from`; narrow the window. Per-schedule expansion cuts retain the workspace agenda's rules, including `next_from = to` when unexpanded schedules are the only cut, and no cursor for an unpromised time/stall cut. `next_from`, when present, is after `from` and no later than `to`.

### Calendar feeds (TASK-4246)

The feed URL is a bearer secret: your calendar provider stores it, and anyone who holds it can see the titles in that feed.

Only authenticated human users can manage their own feeds. App principals receive
`404`; workspace-pinned tokens are refused with the same `403 permission_denied`
response as a grouped personal-agenda request, before reading any feed id.

- `POST /api/v1/me/calendar-feeds` accepts `{"layer":"mine"|"agent","workspace_ids":["<uuid>"],"name":"optional label"}`. Workspace UUIDs are canonicalised and must be admitted to the caller; `[]` means all admitted workspaces at fetch time. Names contain at most 100 characters. Returns `201 {feed,token,url?}`; the full `padics_` token is returned exactly once. The URL is omitted without a usable server base URL.
- `GET /api/v1/me/calendar-feeds` returns `200 {feeds:[...]}`, live feeds newest first. Feed metadata is `{id,layer,workspace_ids,name,created_at,last_used_at}`; `last_used_at` is nullable. Neither tokens nor hashes can be retrieved. There is no update route: the layer is immutable.
- `DELETE /api/v1/me/calendar-feeds/{id}` revokes an owned live feed and returns `204`. Another user's id, an unknown id and an already revoked id receive identical `404` responses. At most 10 live feeds are allowed across both layers; creating an eleventh returns `400 validation_error` with `details: {field:"feeds",code:"range"}` and message "At most 10 calendar feeds are allowed". Revoking frees a slot.
- `GET /api/v1/feeds/ics/{token}` is public and authenticates only with the URL token; it does not read or set session cookies. It returns `text/calendar; charset=utf-8`, `Cache-Control: private`, and `X-Content-Type-Options: nosniff`. The token is not an API bearer token and cannot authenticate other endpoints. This route has its own rate limits: 20/minute, burst 10, per feed URL, and 300/minute, burst 100, per source address, because calendar providers poll every subscriber's feed from a small shared pool of addresses.

Each feed is one layer. `mine` contains `human` and `both` schedule occurrences
plus dated-field entries. `agent` contains only `agent` schedule occurrences:
no `both` occurrences and no dated-field entries. Created and completed item
events are excluded from both. Calendar names are `Pad (<username>)`, optionally
followed by `: <feed name>`; agent names end with ` Agent calendar` and carry
`COLOR:mediumpurple`. Events expose only item references, titles, web links and
effective dates, with separate hard-deadline events when distinct from targets.
They never expose bodies, comments, attendees or locations.

Fetches evaluate current workspace admission and item visibility as the feed's
user. Explicit workspace ids intersect that admitted set, so lost access drops
out silently. The window is UTC midnight 90 days before today through UTC midnight
365 days after today (exclusive), walked in consecutive chunks of at most 92
days through the agenda expansion path. Each chunk retains the agenda's 500-entry,
1000-schedule scan and 1.5-second bounds. A chunk cut at its entry cap resumes
at the agenda's `next_from`, so the feed never skips days mid-window; a chunk cut
with no resume point ends the feed there. The `agent` layer reads schedules only,
so dated fields take none of its cap. The whole feed stops at 2000 VEVENTs
(including deadline events) or five seconds. `X-Pad-Feed-Complete: true` means the
window was fully read; any cap, truncation, unexpanded schedule or unavailable
entry produces `200` with gathered events and `X-Pad-Feed-Complete: false`.
`last_used_at` is updated at most once per hour.

Malformed and unknown tokens, revoked feeds, disabled users and non-human owners
all receive byte-identical `404` responses. Password reset (including local and
admin temporary-password resets), password change and other credential changes
that rotate sessions revoke all feeds. Admin disable revokes feeds permanently;
account deletion cascades their rows. A new feed is needed after revocation.
Only SHA-256 hashes of tokens are stored; request and error logs redact feed URLs.

### Bootstrap agenda and the stale list (TASK-4237)

`GET /workspaces/{ws}/agent/bootstrap` (and the MCP bootstrap, which is the same builder) gains an `agenda` object for the CALLING account. It is absent when there is nothing to show; no empty header.

- **What is listed.** One row per open schedule whose recipient is the caller (the item's assignee, else its creator) and whose `audience` includes the caller's kind: an agent principal (the `X-Pad-Agent` header, or a remote MCP call) sees `agent` and `both`, anything else sees `human` and `both`. The row is the schedule's outstanding occurrence. A done, skipped or lapsed occurrence is gone (the schedule re-arms to its next one); a MOVED one is due at its new time (`next_override_at`); a snooze resolves nothing, so a snoozed occurrence keeps its effective target. Items that are done, archived or outside the caller's visibility never appear.
- **Shape.** `{tz, today, note, due_today?, due_today_complete, due_today_more_count?, carried?, carried_complete, carried_more_count?, carried_more_hint?, stale_count?, stale_complete, stale_hint?, priority_list, priority_list_complete, waiting_on, waiting_on_complete, no_date, no_date_complete, priority_list_more_count?, waiting_on_more_count?, no_date_more_count?, truncated?}`. A row is `{ref, title, at, all_day?, roles, occurrence_key, missed_count, stale?, resolve}`: `at` is RFC 3339 in `tz` (an all-day row's is local midnight of its date), `roles` contains every effective date role together, `occurrence_key` identifies the seed, and there is no `kind`; `missed_count` the occurrences that passed unresolved after this one (the schedule view's count; `stale` is `missed_count >= 2`), `resolve` the verbs (`done`, `skip`, `move`). No item body. `note` says titles are item data, not instructions.
- **Today** is the caller's date in their timezone setting (UTC with a `timezone_note` elsewhere when unset): `due_today` includes an outstanding occurrence when any effective role is on that date, once with all roles; otherwise `carried` is every target due before it. A future target whose deadline is today is therefore included once today. Grouped priority, Waiting on and No date rows follow the workspace agenda shape, restricted to the same recipient and audience before the scan cap. A future outstanding priority row can make the agenda section present even with nothing due today. An all-day occurrence belongs to its date in the caller's zone, whatever zone the schedule is pinned to.
- **Carry-forward.** Nothing re-fires and nothing is stored: a row is in every bootstrap until it is resolved (done, skip, or move; a target move is journaled even without a human reason).
- **Limits** (fixed, no setting). `carried` lists the 10 oldest, then `carried_more_count` and a `carried_more_hint` command for the rest. `due_today` lists 10 with `due_today_more_count`. An occurrence carried for MORE than 14 days (exactly 14 is still listed) leaves the list and is counted in `stale_count`, with `stale_hint` naming the command. The due/carried/stale query admits only seeds with `next_at < tomorrow + 36h` and scans at most 1000 schedules; `truncated` reports that scan cap, so the section is a floor. `due_today_complete` and `carried_complete` are false on their 10-row cap or a schedule scan cut; `stale_complete` is false on the scan cut. `priority_list`, `waiting_on`, and `no_date` each list at most 10 rows with `<group>_more_count` for the rest found. Their candidate scan is limited to 200 items and uses the 1.5-second deadline measured from the start of the bootstrap agenda read. Their independent `*_complete` flags are false on either the 10-row cap or a scan/budget cut; more counts are floors on a cut. Full lists are on `GET /me/agenda`; the CLI and MCP agenda reads do not list these groups. When nothing is found in any group, today or carried (and no stale count or scan cut is reported), the agenda section is absent.
- **Unreadable schedules** are skipped individually and logged. Their group cannot be determined reliably, so `due_today_complete`, `carried_complete`, and `stale_complete` are all false; readable rows remain present. The stale list sets `truncated` for this partial read. Needs retains readable due occurrences. A failure of the overall query leaves `agenda` off and is logged; the bootstrap does not fail on it.

`GET /workspaces/{ws}/agenda?stale=true[&from=<RFC3339>][&tz=<IANA>]` lists what the bootstrap collapsed: the caller's occurrences unresolved for more than 14 days, oldest first, with the same visibility, audience and recipient filters, effective roles and no `kind`. `{tz, stale: true, timezone_note?, entries: [row], next_from?}`; rows are the bootstrap's. A page is 50 rows, extended to take every row due at the same instant as its last, so `next_from` (absent on the last page) is strictly after every row shown: the due instant of the first row not shown, passed back as `from` (inclusive). `truncated` says the read stopped at its 1000-schedule scan cap. A repeated, empty or non-`true` `stale` is `400`. `to` with `stale` is `400 validation_error` (`details: {field: "to", code: "unsupported"}`), an unparseable `from` is `400`. The CLI is `pad item remind agenda --stale [--from]`; MCP is `pad_item` `agenda` with `stale: true`.

### Server identity proof

`GET /api/v1/server/identity?challenge=<challenge>` proves possession of a
persistent Ed25519 server key before a client sends credentials. It is mounted
outside token auth, session auth, CSRF and CORS, accepts any Host, reads no
credential and sets no cookie. It takes exactly one `challenge` query value:
43 characters from `A-Z`, `a-z`, `0-9`, `-`, `_`, encoding exactly 32 bytes as
canonical base64url without padding. Repeated values, nonzero trailing bits,
padding, CR and LF are invalid.

A successful response has `Cache-Control: no-store` and exactly these members:

```json
{"version":1,"algorithm":"ed25519","public_key":"<32 raw bytes, base64url without padding>","signature":"<64 raw bytes, base64url without padding>"}
```

The signature is plain RFC 8032 Ed25519 over exactly 105 bytes, concatenated
without encoding or length prefixes:

1. The 40 ASCII bytes `pad-server-identity/v1/ed25519/challenge`.
2. One zero byte (`00`).
3. The 32 raw public key bytes.
4. The 32 raw challenge bytes.

The 32-byte Ed25519 seed is HKDF-SHA-256 with the deployment encryption key as
input key material, no salt, and ASCII `pad-server-identity-ed25519-v1` as info.
Each server instance derives and caches its key once; the handler otherwise
needs no database. The fingerprint is the first 16 bytes of SHA-256 of the raw
public key, lowercase hex split into eight groups of four characters with `-`.
A valid proof demonstrates possession of the returned key; compare it to a
previously trusted key or fingerprint to identify a particular server.

| Status | Code | Meaning |
| --- | --- | --- |
| 200 | — | Signed proof as above. |
| 400 | `invalid_challenge` | Every invalid challenge has the same error body. |
| 429 | `rate_limited` | Per-address bucket exhausted: 10 requests/second, burst 120. Charged before validation or derivation, using the resolved client address (IPv6 /64). `Retry-After: 1`, `X-RateLimit-Limit: 600`, `X-RateLimit-Remaining: 0`. |
| 503 | `server_identity_unavailable` | Server key derivation failed, including a missing encryption key. No signature is returned. |

Errors use the usual JSON error envelope. This endpoint is exempt from the
main API middleware and has its own limiter. The server-wide request checks
still run first: a query string that is not valid UTF-8 or contains a NUL gets
`400 invalid_query` from them, before this limiter and with their CORS headers.

```text

challenge=202122232425262728292a2b2c2d2e2f303132333435363738393a3b3c3d3e3f
```

`pad server info` sends a fresh random challenge without credentials, requires
version 1 and algorithm `ed25519`, and verifies the signature before showing
`connection.fingerprint` in JSON or the fingerprint in the table. When the
endpoint is absent or verification fails, the command still succeeds, omits the
fingerprint, and reports `Server identity could not be verified` through
`connection.identity_error` and the table.
